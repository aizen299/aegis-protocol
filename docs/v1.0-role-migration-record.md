# Role migration — execution record

Build-order step 5 of `docs/v1.0-production-plan.md`: perform the migration in
`docs/role-migration.md`, stages 1–3, and record what was run.

**Where this ran: a local Anvil chain, not staging.** The plan originally called for staging; that
deployment is deferred for want of an AWS account (`DEFERRED.md`). A local chain exercises the
procedure and the contracts; it does not exercise a real multisig, real signers, or the operational
reality of a migration performed by people under time pressure. The release notes say so.

**Date:** 2026-09-15. **Chain:** Anvil, chain id 31337.

---

## What was migrated

One role — `VAULT_MANAGER_ROLE` on `VaultEngine` — through all three stages. Not the full sequence
in the runbook's table: `ORACLE_MANAGER_ROLE`, `PAUSER_ROLE`, and `UPGRADER_ROLE` have not been
migrated, on any chain. What this establishes is that the procedure works end to end for one role
against separately deployed contracts, which is the form an operator performs it in.

Stage 4 (`DEFAULT_ADMIN_ROLE`) was not performed and is out of scope for v1.0. It is irreversible
and the runbook requires every other role to have a governance track record first.

`SLASHER_ROLE` was not migrated and never will be. The record below checks that it did not move.

## Reproducing this

```bash
make e2e
```

Or, against an Anvil already running on 8545:

```bash
cd backend && go test -tags e2e ./internal/e2e/ -run TestRoleMigrationOnALocalDeployment -v
```

The procedure is executed by `backend/internal/e2e/role_migration_test.go`, which deploys the vault
and the governance stack separately and copies addresses between them. Running it reproduces the
transcript below with fresh addresses.

## What each stage established

**Stage 1 — grant while the multisig retains.** `grantRole(VAULT_MANAGER_ROLE, timelock)` sent by
the deployer, which stands in for the multisig. Both hold the role afterwards, and the governor
holds nothing — the runbook's central claim, since granting the governor instead looks identical
until the first execution fails.

**Stage 2 — exercise it through a proposal.** A real parameter change with an observable value:
`setDepositCap(777e18)` on the vault, proposed, voted, queued, delayed, executed. The cap was
checked after queueing and before the delay elapsed and had not moved — the delay is what the
timelock is for, and a test that only checks the end state would pass against a timelock that
executed immediately.

The proposer delegated to itself and let one second pass before proposing. That is not incidental:
`Governor.propose` reads voting power one tick back, so power delegated in the same second does not
count. An operator migrating roles must delegate before proposing, not in the same transaction.

**Stage 3 — the multisig renounces.** `renounceRole` sent by the deployer. Afterwards the deployer
no longer holds the role, a direct `setDepositCap` from the deployer reverts, and the timelock still
holds what it was granted. The negative check matters as much as the positive one: a migration that
left the old holder able to act has migrated nothing.

**The negative space.** `SLASHER_ROLE` was checked on the timelock and is absent. A migration that
granted more than intended is invisible in a per-role check of the roles you meant to grant.

## What this does not establish

- Nothing about a real multisig: signer thresholds, transaction batching, or the coordination cost
  of getting signatures for each stage.
- Nothing about the other three roles in the suggested sequence.
- Nothing about stage 4, which is where the decision becomes irreversible.
- Nothing about performing this on a public chain, where a queued proposal is visible to anyone for
  the duration of the delay.
