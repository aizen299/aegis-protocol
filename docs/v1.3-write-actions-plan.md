# v1.3 — Write actions, and proving in the browser

The UI reads the whole protocol and writes to none of it except the vault. This adds the governance
write path, and the zk proving path — the second of which is an architectural decision, not a
feature.

---

## 1. Scope

**In:** governance `castVote`, `queue`, `execute`; zk `executePrivateAction` with the proof generated
in the user's browser.

**Out, with reasons:**

- **`propose`.** A proposal carries arbitrary calldata, so a UI for it is a calldata builder — its
  own design problem, and a malformed proposal is permanent on-chain spam. Deferred until the
  governance write path has been used for something reversible first.
- **Oracle staking and registration.** Operator tooling that moves real stake. Belongs with the
  ORC-1 work, not here.
- **Vault deposit and withdraw.** Already exist, and gained slippage bounds in v1.2.

## 2. Decisions

### 2.1 Proofs are generated in the browser, not by a hosted service

`docs/zk.md`'s architecture routes private inputs to the Rust proof service. **This deviates from
that, deliberately, and the deviation is recorded.**

The circuit derives both of a user's identities from one secret: `commitment_of(secret)` is the leaf
they deposited at, and `nullifier_of(secret, ...)` is the spend. `ProveRequest` carries the secret
and the nullifier hash in the same body, so a hosted prover receives both halves together and can
build exactly the table `migration 000008` refuses to store — deposit linked to spend, for every
user who uses it.

The service is careful with what it receives: inputs are zeroized on drop, `PrivateInputs` has no
`Serialize` impl so it cannot reach a response body, and nothing is logged. But that is the operator
behaving well, not a property of the system. TLS termination, a crash dump, a memory-scraping host,
or a legal order all defeat it.

A privacy module whose guarantee reduces to "trust whoever runs the prover" has relocated the
problem rather than solved it. Browser proving keeps the secret on the device; what crosses the
network is `(proof, publicInputs)`, which is what the proof exists to make sufficient.

**Cost, stated plainly:** a multi-megabyte WASM bundle, proving that takes seconds rather than being
instant, and a second proving implementation — see §2.2.

### 2.2 Two proving paths must agree, and that is checked rather than assumed

The Rust service shells out to the `nargo` and `bb` binaries. The browser will use `@noir-lang/noir_js`
and `@aztec/bb.js`. Two implementations that must produce proofs the same committed verifier accepts.

This project has been bitten four times by two things that were supposed to agree with nothing
enforcing it: the ABI, the Poseidon artifact, the verifier, and the frontend's API types. Each time
the fix was a check, and each check found a real defect on its first run.

So: the JS packages are pinned to **exactly** the versions that generated the committed verifier —
`noir_js@1.0.0-beta.22` and `bb.js@5.0.0-nightly.20260522`, matching `zk/circuits/toolchain.txt` —
and a test generates a proof through the browser path and verifies it against the committed verifier.
A version bump on one side without the other must fail, not drift.

### 2.3 The Rust proof service keeps its tests and gains a stated role

It has no caller. Nothing in the backend or frontend has ever invoked it, in four releases — the same
shape as the frontend API client that was dead code long enough to hide a wrong type.

It is not deleted: it is the reference implementation the browser path is checked against, and the
only place the CLI proving path is exercised under test. But its status is written down rather than
left ambiguous — **it is not a user-facing prover, and must not be offered as one without the
disclosure in §2.1.**

### 2.4 Delegation is surfaced before the action, not after the revert

Promised in `docs/v1.1-frontend-plan.md` §2.2, due here.

`castVote` reads `getPastVotes` at the proposal's `voteStart`. A holder who never delegated has zero
voting power, and self-delegating now does nothing for a proposal whose snapshot has passed. v1.0's
GOV-1 fix adds a second: `propose` reads power one tick back, so delegating and proposing in the same
transaction fails by design — the break that took out five end-to-end tests when it landed.

The UI shows delegated power beside balance and disables voting with the actual reason — "you had no
delegated voting power when this proposal's snapshot was taken" — rather than surfacing a revert.

### 2.5 A transaction has four states, and they stay distinguishable

Idle, signing, pending, and settled — plus failed, which is not the same as any of them. The read
path already refuses to collapse loading, failed, and absent into one rendering; the write path
inherits that rule. A submitted transaction that reverted must never look like one that succeeded,
and a pending one must never look like either.

## 3. Invariants

- No secret leaves the browser. Nothing in the client sends `secret`, `pathElements`, or
  `pathIndices` over the network, and a test asserts it.
- A proof generated in the browser verifies against the committed verifier.
- The JS proving packages match `zk/circuits/toolchain.txt` exactly; a mismatch fails the build.
- Voting is disabled with a reason, never enabled into a revert.
- A failed transaction is reported as failed.

## 4. Build order

1. Pin the JS proving packages and prove the browser path agrees with the committed verifier. This
   is first because it is the step that can fail — everything else is UI on top of it.
2. Governance writes: vote, queue, execute, with delegated power shown and §2.4's reason.
3. The zk proving flow: witness assembly in the browser, proof generation, submission.
4. Record the §2.1 deviation, and the Rust service's stated role, in `DEFERRED.md`.

Step 1 first so an infeasible browser path is discovered before any UI is built on the assumption
that it works.

## 5. What building it found

**Step 1 — browser proving.** Feasible, and exactly matched: the JS packages exist at the pinned
toolchain versions, and a WASM-generated proof verifies against the committed verifier. Two traps
on the way, both silent. `Barretenberg.new()` in Node prefers the native `bb` binary, so the check
would have tested the CLI against itself; the backend is forced to WASM. And `{ keccak: true }`
disables ZK, producing a 7424-byte proof the 8384-byte verifier rejects; `verifierTarget: "evm"` is
the option that matches `gen-verifier.sh`.

On its first clean runner the check failed twice before proving anything — `circomlibjs` and then
`forge` were installed on the development machine and nowhere else. Both are now preflighted by
name. The third run is the first that exercised browser proving off that machine.

**Step 2 — governance writes.** Building the transaction state found a defect already shipped in
the v1.2 vault forms: the hash turned green on *submission*, and no code read the receipt's status.
wagmi resolves a reverted transaction rather than erroring, so a deposit reverted by its own new
slippage bound displayed as one that landed. Transactions now resolve to signing, pending,
confirmed, reverted, or failed, and reverted is never confirmed.

The executable-time check compares against the latest block's timestamp, not the browser's clock.
They agree on a live network and diverge by days on a local chain that has been time-warped, which
is how every governance test here reaches its timelock.

The frontend's hand-written ABIs are now checked against the backend's committed ABIs, which are
themselves checked against `forge`. Reverting the frontend's `deposit` to its pre-v1.2 signature
fails with the signature named.

**Verified end to end, with a test wallet.** A wagmi mock connector over Anvil's first development
account signs through `eth_sendTransaction`. It is enabled only when `NEXT_PUBLIC_TEST_WALLET=anvil`
*and* the chain is 31337 — both required, each tested alone — because those keys are public, and a
UI offering them against any other chain would be offering to sign with a key everyone has.

With it, a vote cast through the UI landed on chain: receipt success, the `castVote` selector, sent to
the Governor, `hasVoted` true, and indexed as support 1 with the full delegated weight.

**Doing so found a defect in step 2's own fix.** Execute was offered on a queued proposal two days
before the timelock would accept it. The executable time came from the API; the queue event was not
yet indexed; and the check skipped itself when the time was absent, defaulting to allowed. A missing
block time likewise fell back to the browser's clock — the divergence a comment in the same function
warned about. Both now read from the chain (`proposalOf(id).executableAt` and the latest block), and
an unknown time refuses rather than permits.

The check was then shown to discriminate: with the chain warped ten days past the browser's clock,
Execute enabled while the browser's own clock said not yet. Only chain time could have enabled it.

The drift test was deepened at the same time. It compared a struct return's type as `"tuple"` alone,
so a retyped field inside `proposalOf` would have passed; it now compares shapes all the way down.

**One transaction reverted, correctly.** The test proposal called `setDepositCap`, and the timelock
had never been granted `VAULT_MANAGER_ROLE` — stage 1 of the role migration, skipped in the test
setup. The Governor reverted with `AccessControlUnauthorizedAccount`. The UI showed it as pending, not
confirmed, which is the defect step 2 fixed. It did not visibly resolve to *reverted*: the browser
pane was hidden, which pauses React Query's interval refetching and throttles receipt polling. That
transition is covered by unit tests and was not observed live.

The same hidden-tab pause froze the block read, so chain time went stale. That errs safely — a stale
chain time is always earlier than the true one, so it refuses rather than permits — and a real user
returning to a backgrounded tab gets a refetch on focus.

**Step 3 — the proving flow.** Built and verified end to end against a real chain: a deposit's secret
entered in the page, the tree rebuilt locally, the proof generated in the browser, and the proof
submitted by the test wallet. The receipt succeeded, the gate emitted a nullifier identical to one
derived independently in a separate process, and that nullifier is spent. The on-chain verifier
accepted a proof that was generated inside a web page.

Proving took about twenty seconds in a hidden, throttled browser pane. The UI says so before it
starts, rather than showing an unexplained spinner.

A spike came first, because in-browser WASM inside Next.js was the step most likely to fail. It did
not fail — no bundler configuration was needed — but the first attempt appeared to, because running
`next build` while `next dev` was serving had overwritten the dev server's `.next` output, leaving a
page that could never hydrate. The prover was not at fault. Builds are now run with the dev server
stopped.

The browser's Poseidon and tree rebuild are checked against two references: the committed proof
fixture, which pins the circuit and verifier, and roots read from `CommitmentTree.sol` after inserting
three leaves in order. The single-leaf fixture only exercises left children and zero siblings; the
contract roots cover right children and real siblings. A skip was briefly left where those vectors
should be and was replaced with the real values before this was recorded — a skipped test reports
green while proving nothing. Swapping the hash order fails both.

The compiled circuit the browser loads is a committed copy of a gitignored build artifact, checked
against a fresh compile in zk CI. Only `abi` and `bytecode` are kept: the compiler's `file_map` and
`debug_symbols` held absolute paths from the development machine, which would have published a local
username in a public web asset and could never have matched a CI runner's paths.

**Privacy, verified two ways.** A unit test records every request made while assembling a witness and
forbids the secret, the commitment, and the nullifier from appearing in any of them; it fails, naming
the leaked value, when the commitment is looked up through the API instead of locally. In the live
run, 39 requests were inspected: the tree was fetched only as `limit=100&offset=0`, and no URL carried
the secret or the commitment.

That live check reads URLs, not POST bodies. By inspection, the RPC reads made before submission send
the root and the nullifier — never the secret or the commitment. The root is public and shared by
every depositor. The nullifier becomes public on submission, and the RPC operator sees that submission
anyway, so learning it a moment earlier links nothing new.
