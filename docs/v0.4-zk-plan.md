# v0.4 zk Privacy Layer — Implementation Plan

Working document, not a locked spec. `docs/project-spec.md` §7 and `docs/zk.md` remain the
reference; this records how v0.4 gets built and where it proposes to diverge.

**Status:** §2.1-§2.7 approved. §2.7 is implemented as an explicitly domain-separated,
action-specific authorization gate. §2.3, §2.4, and §2.6 are corrections to defects in
`docs/zk.md`, not optional choices.

**Was:** awaiting sign-off on §2. Seven decisions. One is the framework choice `docs/zk.md` says
must be finalised pre-May; three correct defects in that document's circuit sketch; one extends a
locked §7 constraint.

---

## 1. Scope

**In:** a commitment set the vault maintains on chain, a membership circuit, a generated verifier,
a nullifier-gated action contract, and the Rust proof service that produces proofs for it.

**Out, deliberately:**

- **No anonymous transaction graph.** `docs/zk.md` is explicit: scope is proof-of-membership and
  selective disclosure, not a mixer.
- **No private voting.** `docs/zk.md` lists it as post-v0.4. Governance already works; adding
  anonymity to it is a separate design with its own coercion and quorum questions.
- **No private balances.** Proving *membership* without revealing *which* member is the v0.4
  claim. Hiding amounts is a different circuit and a different threat model.

## 2. Decisions needed before code

### 2.1 Noir, not Circom — *the choice `docs/zk.md` defers to this point*

`docs/zk.md` gives the criterion directly: "Circom if the team has prior constraint-system
experience. Noir if starting fresh." This project is starting fresh. Three further factors decide
it the same way:

| Factor | Circom + snarkjs | Noir + Barretenberg |
|---|---|---|
| Setup | Groth16: a **per-circuit** Phase 2 ceremony | UltraPlonk: universal SRS, no per-circuit ceremony |
| Cost of a circuit change | Re-run the ceremony | Recompile |
| Rust integration | WASM/FFI | Native |

The setup row is the deciding one. A per-circuit ceremony is not a one-time cost — it recurs on
every circuit change, and the circuit will change many times during v0.4. `docs/zk.md` also says an
internal ceremony is acceptable for v0.4 but that v1.0 should "consider a public ceremony or switch
to Plonk/UltraPlonk". Choosing Circom means building a ceremony process, repeating it on every
iteration, and then throwing it away at v1.0.

**Proposed:** Noir with Barretenberg. (The verifier command named here was corrected in §2.9: `nargo codegen-verifier` no longer exists.)

**Costs, stated:** the generated UltraPlonk verifier is larger and more gas-expensive than a Groth16
one, and Noir's toolchain moves fast — the `nargo` and `bb` versions must be pinned exactly and
recorded, the same discipline `solc_version` already gets.

**What does not change:** the verifier is generated, never hand-written. That is locked in
`docs/zk.md` and holds either way.

### 2.2 The commitment set lives on chain — *not stated in `docs/zk.md`*

`docs/zk.md` describes a Merkle root as a public input but never says who maintains the tree. It is
the load-bearing question: whoever controls the root controls who can prove membership.

| Owner | Problem |
|---|---|
| The Go backend, posting roots periodically | Makes the backend authoritative over set membership. `project-spec.md` §10 puts the backend in the intelligence layer, not the settlement layer, and a forged root mints membership |
| An off-chain tree with on-chain root commits by a role | Same trust, wearing a role |
| An on-chain incremental Merkle tree | Gas per insert |

**Proposed:** an on-chain incremental Merkle tree. Insertion happens in the contract, the root is
always current and never asserted by an off-chain party, and the indexer *mirrors* the tree to
generate proofs. If the mirror is wrong, proofs fail to verify — a liveness bug. If a posted root
were wrong, membership is forged — a solvency bug. Gas is the right thing to spend here.

### 2.3 Nullifiers are scoped, not global — *corrects `docs/zk.md`*

`docs/zk.md` computes `nullifier = Poseidon(secret, 1)`. The `1` is a constant, so a secret yields
exactly one nullifier for all time: **a user can perform exactly one private action, ever.** That
is almost certainly not the intent, and it is invisible until the second action reverts.

**Proposed:** `nullifier = Poseidon(secret, externalNullifier)`, where `externalNullifier` is a
public input identifying the action being gated. One action per secret per external nullifier,
which is the property a gate actually wants.

### 2.4 The circuit must bind the commitment into the Merkle path — *corrects `docs/zk.md`*

The sketch in `docs/zk.md` computes `commitment = Poseidon(secret)`, then elides the Merkle
verification as "... standard Merkle path computation", and never constrains the two together. As
written, the circuit proves knowledge of a secret **and, independently,** knowledge of some valid
path — not that the path leads to *this* secret's commitment.

**Proposed:** the leaf fed to the path computation is the commitment signal itself, and the plan's
invariants make that an explicit test: a proof built from one account's secret and another's path
must fail.

### 2.5 A nullifier is chain-scoped — *extends §7 constraint 1*

`project-spec.md` §7 requires cross-layer identity to be 32 bytes; a nullifier already is. But
Phase 2 deploys independently per chain, and a nullifier map that is not chain-scoped means a proof
spent on one chain can be replayed on another. This is the same replay class that put `chainId` in
the v0.2 EIP-712 payload.

**Proposed:** `chainId` is a public input to the circuit and is bound into the verifier call, and
the on-chain nullifier map is keyed per chain. In Phase 1 there is one chain and this is inert; the
cost of adding it now is one public input, and the cost of adding it later is a redeployment.

### 2.6 The proving key is not a secret — *clarifies `docs/zk.md`*

`docs/zk.md` lists "proving key exposure" as a risk with the mitigation "stored server-side only,
never sent to client". Under Plonk that is a bandwidth decision, not a security one: the proving
key and the universal SRS are public, and soundness does not depend on withholding them. Recording
it as a secret invites the wrong operational handling — key rotation procedures for a public
artifact, and an assumption of safety that does not exist.

**Proposed:** treat the proving key as a large public artifact: pinned by hash, served from S3,
verified on load. The genuine secrets in this layer are the users' — and those never leave the
client's request body, are never logged, and are zeroized after use.

### 2.7 What the gate actually gates

A verifier with nothing behind it is a demo. The v0.4 action is deliberately small and observable:
**prove membership in the vault's depositor set without revealing which depositor**, to pass a gate
that records the action against a nullifier.

That is enough to exercise the whole path — commitment, tree, proof, verifier, nullifier, replay
rejection — without inventing a privacy product the protocol has not specified.

### 2.8 The hash is circomlib-compatible Poseidon, not Poseidon2 — *found while building §2.2*

§2.2 puts the Merkle tree on chain, which means the contract computes the same hash the circuit
does. That requirement was not costed when §2.1 chose Noir.

Noir's default is Poseidon2, and **no audited Solidity implementation of Barretenberg's Poseidon2
exists**. Using it would mean hand-porting round constants and the MDS matrix into the contract
that builds the tree — hand-writing a cryptographic primitive, which `docs/zk.md` forbids for the
verifier and which is worse here: a single wrong constant produces a tree no proof can ever verify
against, and the failure appears only at integration.

Noir also ships a circomlib-compatible Poseidon. It was verified against circomlib's canonical
vectors before anything was built on it:

| Input | Value |
|---|---|
| `hash_1([1])` | `0x29176100eaa962bdc1fe6c654d6a3c130e96a4d1168b33848b897dc502820133` |
| `hash_2([1, 2])` | `0x115cc0f5e7d690413df64c6b9662e9cf2a3617f2743245519e19607a4417189a` |

**Proposed:** the circuit uses `poseidon::poseidon::bn254`, and the contract uses a generated
circomlib Poseidon checked against the same vectors. This is the arrangement Tornado Cash uses, and
it keeps the "never hand-write the primitive" rule on both sides of the boundary.

**How the artifact is managed** — approved: generated deterministically from circomlibjs pinned to
an exact version with a committed lockfile, emitted as Solidity into
`contracts/src/zk/poseidon/PoseidonBytecode.sol`, and committed. `make poseidon-gen` regenerates;
`make poseidon-check` regenerates into a temp directory and fails on any difference, wired into
Contracts CI as its own job. Node is required only for regeneration — `forge build` and `forge test`
read the committed artifact, verified by deleting `node_modules` and running both. Emitting Solidity
rather than a raw bytecode file also keeps the contracts suite free of filesystem permissions.

**Cost, stated:** Poseidon2 is cheaper in circuit, so this raises constraint count and proving
time. That is the right trade — an on-chain hash that cannot be verified to match the circuit is
not a performance question.

**Pinned by test:** the other seventeen circuit tests pass under any hash function, because they
test structure rather than the primitive. `the_hash_family_is_circomlib_compatible` and
`the_commitment_uses_the_pinned_hash` are the two that fail if the family is swapped — verified by
mutation.

### 2.9 The toolchain pin moves down to nargo 1.0.0-beta.22 — *found while starting §5 step 3*

§2.1 pinned nargo at 1.0.0-beta.26, chosen only because it was what `noirup` installed as "latest
stable". Two things were wrong with that, both invisible until a verifier was actually needed:

**`nargo codegen-verifier` no longer exists.** `docs/zk.md` names it and §2.1 repeated the claim.
Verifier generation moved to Barretenberg (`bb write_vk` then `bb write_solidity_verifier`).

**bb is not independent of nargo, and beta.26 has no compatible bb.** Aztec publishes a
compatibility map at `barretenberg/bbup/bb-versions.json`; its newest entry is **beta.22**. A nargo
newer than the map has no usable bb at all, so no verifier could be generated and step 3 was
impossible as pinned.

**Proposed:** nargo `1.0.0-beta.22` with bb `5.0.0-nightly.20260522`, the pairing that map declares.
Verified rather than assumed: the circuit's 19 tests pass unchanged on beta.22 with the same
poseidon v0.3.0, and the full pipeline runs — compile, VK, Solidity verifier, proof, and native
verification.

`make zk-toolchain-check` now checks bb as well as nargo, because a matching bb is a precondition
for producing a verifier at all rather than a nice-to-have.

### 2.10 The verifier's interface is not the one `docs/zk.md` documents

`docs/zk.md` sketches a Groth16 shape:
`verify(uint256[2] a, uint256[2][2] b, uint256[2] c, uint256[] publicInputs)`.

Barretenberg's generated UltraHonk verifier is `verify(bytes proof, bytes32[] publicInputs)`.
`ZkVaultGate` is built against the generated interface, not the sketch.

One detail worth recording because it reads as a contradiction: the generated verifier declares
`NUMBER_OF_PUBLIC_INPUTS = 13` while the circuit has 5. The extra 8 are the pairing point object bb
carries inside the proof; the caller supplies only the 5. Confirmed by generating a real proof —
its `public_inputs` file is exactly 5 fields, in declaration order, with `chain_id` reading 31337
and `gate` reading `0xab` as supplied.

**Free cross-check.** The witness fed to that proof was computed entirely in circomlibjs, and the
circuit accepted it. The Noir circuit, circomlibjs, and the generated Solidity Poseidon are now all
confirmed to agree on the same values — §2.8's claim, verified from a third direction.

## 3. On-chain design

| Contract | Holds | Upgradeable |
|---|---|---|
| `CommitmentTree` | the incremental Merkle tree and its root history | UUPS |
| `ZkVerifier` | generated verification logic | no — regenerated, redeployed, never edited |
| `ZkVaultGate` | nullifier map, gating logic | UUPS |

`ZkVerifier` is not upgradeable because it is generated output. A change to it means a new circuit,
which means a new verifier address the gate is pointed at — an upgrade of the *gate*, reviewable as
such.

### Root history

A proof is built against a root that was current when the prover read the tree. If a deposit lands
between reading and submitting, the root moves and a correct proof fails. `CommitmentTree` therefore
keeps a bounded window of recent roots and the gate accepts any of them — a known and necessary
design, and the window size is a parameter with a stated trade-off: too long widens the set an old
proof is valid against.

### Events

```solidity
event CommitmentInserted(uint256 indexed leafIndex, bytes32 indexed commitment, bytes32 root);
event RootUpdated(bytes32 indexed root, uint256 leafCount);
event PrivateActionExecuted(bytes32 indexed nullifier, bytes32 indexed root, uint256 chainId);
```

`CommitmentInserted` carries the leaf index and the resulting root so the indexer can rebuild the
tree without replaying contract state — the rule that made `ProposalCreated` carry its whole action.

## 4. Risk register

| Risk | Severity | Mitigation | Residual |
|---|---|---|---|
| Proof replay | High | nullifier map, chain-scoped (§2.5) | none |
| Forged membership via a bad root | High | tree is on-chain (§2.2) | none |
| Circuit proves secret and path independently | High | §2.4, with a negative test | none |
| One action per user, forever | Medium | §2.3 | none |
| Private inputs leaked in logs | High | never logged, zeroized on drop; enforced by test | operator with memory access |
| Verifier bug | High | generated only; valid *and* invalid proof tests | trust in Barretenberg's codegen |
| Toolchain drift changes the verifier | Medium | `nargo`/`bb` versions pinned and recorded; verifier diffed in CI like the ABIs | none |
| Anonymity set of one | **Medium, unresolved** | — | see below |

**Unresolved:** privacy is bounded by the anonymity set. With few commitments in the tree, "one of
N depositors" is weak, and with N=1 it is nothing. No circuit fixes this — it is a property of
adoption. It must be stated in the API response and the UI rather than implied away, and v0.4
should surface the current leaf count wherever a proof is offered.

## 5. Build order

Each step ends green and independently reviewable. The end-to-end test comes before the backend
work, which is the ordering v0.2 and v0.3 both arrived at.

1. Pin the toolchain; the membership circuit in Noir with its own tests, including the negative
   cases from §2.4. — *done. `zk/circuits/vault_membership`, 16 tests, pinned to nargo
   1.0.0-beta.26 and poseidon v0.3.0 in `zk/circuits/toolchain.txt` and enforced by
   `make zk-toolchain-check`. §2.7 is implemented as an explicitly domain-separated,
   action-specific gate: the nullifier binds (secret, action_id, chain_id, gate). Each negative
   test asserts the reason it failed, not only that it did — which caught a swapped argument pair
   on the first run. The suite is mutation-checked: removing the root binding, the path-index
   constraint, or the domain separation each breaks exactly the tests that exist to catch it, and
   restoring the literal `Poseidon(secret, 1)` from `docs/zk.md` breaks five.*
2. `CommitmentTree` with the incremental insert and root history. — *done. 19 tests. The
   incremental insert is checked against a full rebuild from every leaf, and a path taken from the
   tree is walked the way the circuit walks it and must reach the same root. Zero subtrees are
   computed in the initializer rather than hardcoded, since hardcoding them means hand-writing
   values derived from Poseidon. Duplicate commitments are rejected: two identical commitments
   share a nullifier, so only one could ever be spent. `make zk-depth-check` compares the depth
   constant in the circuit and the contract, which no compiler can do across the two languages.*
3. Generate `ZkVerifier`; wire `ZkVaultGate` with the nullifier map; valid and invalid proof tests.
   — *verifier done; the gate is next. `contracts/generated/HonkVerifier.sol` is generated by
   `make zk-verifier-gen` and checked by `make zk-verifier-check`, which catches a one-level change
   in tree depth. A real Barretenberg proof verifies on chain, and tampering with any of the five
   public inputs, the proof, its length, or the input count is rejected — six tests. Verification
   costs ~2.24M gas.*

   *The generated source sits outside `contracts/src` because Slither 0.11.5 crashes parsing it,
   and Slither over hand-written code is mandatory here. Foundry still compiles and links it, since
   the tests import it. It cannot be committed as bytecode the way Poseidon is: it links two
   external libraries, so its creation code carries unlinked placeholders.*
4. Fuzz and invariants; Slither; record the `v0.4.0` layout baselines.
5. End-to-end: a real proof, generated by the service, verified on a real chain, replay rejected.
6. The Rust proof service: tree mirroring, proof generation, the zeroization test.
7. Migration `000008`, indexer handlers, read endpoints.
8. Extend the end-to-end suite through the indexer and API.

## 6. Invariants worth stating up front

- A nullifier is accepted at most once per chain.
- A proof verifying against a root the tree never held is rejected.
- A proof built from one account's secret and another account's path is rejected.
- The commitment set only grows; a leaf is never removed or overwritten.
- A leaf's index in the mirrored tree equals its index on chain.
- A private action reveals nothing on chain beyond the nullifier, the root, and the chain id.
- No private input ever appears in a log line or a response body.
