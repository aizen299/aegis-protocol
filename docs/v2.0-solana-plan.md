# v2.0 — Solana

Phase 2 of `docs/project-spec.md`: a second chain. Solana is the confirmed target, and the spec's §7 is
binding on how it is added — read it first. This plan records the decisions taken at the start of
Phase 2, the decisions that follow from them, and the order in which the work is built.

**Nothing here is built yet.** §2.4 onward are proposals that need sign-off before code.

---

## 1. What the spec already decides

Three constraints are not open, and every decision below is made inside them:

- **Oracle prices do not cross chains.** Each chain runs its own oracle node set, with its own staking
  and slashing. Routing prices over a bridge would replace trust-minimised aggregation with the
  bridge's trust assumption, which is strictly weaker.
- **Vault accounting does not cross chains.** Each chain's vault has its own TVL and share price. A
  user with positions on two chains holds two positions. Unified accounting would let a bridge failure
  corrupt solvency on the healthy chain too.
- **Governance is the only sanctioned cross-chain message.** One DAO, on Arbitrum, whose passed
  proposals can execute on Solana. The receiving side must impose a timelock on inbound messages, be
  pausable, and enforce per-message and rolling value caps.

## 2. Decisions

### 2.1 Messaging layer: Wormhole — *decided*

Chosen for the specific pairing. Solana↔EVM is the route Wormhole was built around and has carried
longest, with the deepest tooling on both sides; for the alternatives, Solana is one destination among
many. Its trust assumption is also legible: a fixed guardian set, whose signatures on a message —
a VAA — are what the receiving chain verifies.

**The counterpoint, held rather than dismissed:** Wormhole is the option that was exploited, on its
Solana side, for about $320M in 2022. The flaw was in signature verification and has been fixed. What
this plan takes from it is not a reason to choose differently but a requirement on the receiver:
**a forged VAA must be survivable.** Every control in §2.9 exists because the guardian set is a single
point of trust, and the design assumes it can fail.

### 2.2 Modules on Solana: vault, oracle, governance receiver — *decided*

**The zk gate is deferred past v2.0.** Its verifier is generated for Solidity by the pinned
Barretenberg toolchain, and there is no equivalent generated verifier for Solana programs. Bringing it
over means a different proof system or a hand-written verifier, and the project's rule is that
verifiers are generated, never hand-written. Recorded in `DEFERRED.md` when this plan is approved.

### 2.3 Build order — *decided as "all three"; sequenced here*

All three modules ship in v2.0. The order below follows dependency, not preference, and can be changed:

1. **Vault first.** It proves the whole Solana path — an Anchor program, a second chain client, the
   indexer, the API, the UI — with no bridge involved.
2. **Oracle second.** The largest program, with no bridge dependency either.
3. **Governance receiver last.** The only piece that touches Wormhole, so it is built on top of a
   Solana path that already works rather than alongside one that does not.

### 2.4 Anchor, and events recorded as CPI data rather than logs — *decided / proposed*

Anchor is decided. It generates an IDL the indexer decodes from — the same role ABIs play today — so
the existing drift-check pattern carries over, and its account constraints rule out the missing
signer and owner checks behind most Solana exploits.

**Proposed: events are emitted with `emit_cpi!`, not `emit!`.** `emit!` writes events to program logs,
and Solana RPC nodes truncate transaction logs past a size limit. An event dropped from a log is an
event the indexer never sees — a deposit that silently never reaches Postgres. `emit_cpi!` records the
event as the data of a self-invocation, retrieved from the transaction's inner instructions, which are
not truncated.

### 2.5 Transaction identity is not 32 bytes — *proposed; a gap in Phase 1*

The spec's Phase 1 constraints required account identity to be 32 bytes. They did not cover
transaction identity. `chain.Event.TxHash` is `[32]byte`, and every indexed row is identified by
`(chain_id, tx_hash, log_index)` — but a Solana transaction is identified by its signature, which is
**64 bytes**.

The database is already safe: every `tx_hash` column is `TEXT` with no length or format constraint. The
assumption lives in the Go type and in the indexer's hex encoding.

**Proposed:** `TxHash` becomes the chain's canonical string form, produced by the chain client the way
`EncodeIdentity` already produces account identities — `0x`-hex for EVM, base58 for Solana. No
migration. An architecture test asserts no shared type fixes a transaction identifier's width.

### 2.6 A chain id for Solana — *proposed*

Every chain-derived row carries a `BIGINT chain_id`. EVM chains have numeric ids; Solana clusters do not.

**Proposed:** each Solana cluster is assigned a stable `int64` in a single registry in the backend,
recorded in this plan when step 1 lands, with a test that fails if any two chains share an id.

*Corrected in step 1:* Phase 1 had already reserved a range for this — ids from `2^62` up are never
EVM chain ids — so assignments come from that range rather than relying on the test alone.

### 2.7 Finality — *proposed*

The indexer reads Solana at `finalized` commitment. Solana's equivalent of the EVM confirmation window
is not a slot count but a commitment level; indexing at `confirmed` would index blocks that can still
be dropped. The Solana client reports a confirmation depth of zero and treats the finalized slot as the
safe head.

### 2.8 Oracle signatures on Solana — *proposed*

Nodes sign submissions with ed25519, verified on chain through Solana's native Ed25519 program. The
signed message carries the program id, the cluster's chain id, the round, and the node's nonce — the
same replay protection the EVM side gets from EIP-712's chain id and contract address, so a signature
for one cluster or program cannot be replayed against another.

Slashing keeps the existing key policy: the slasher key resolves through the same environment-declared
secret source as the EVM one, and staging never falls back to a development key.

### 2.9 The governance receiver — *binding requirements, plus proposals*

Required by the spec: an execution timelock, a pause authority, and per-message and rolling value
caps. Proposed in addition:

- **An emitter allowlist of exactly one.** A VAA is accepted only if emitted by the Arbitrum dispatcher
  contract on Arbitrum's Wormhole chain id. Any other emitter is rejected before anything else is read.
- **Replay protection.** Each accepted VAA's hash is recorded in an account; a second submission of the
  same VAA fails.
- **An instruction payload bound to its accounts.** The payload names the target program, the
  instruction data, and a hash of the account list. The executing transaction supplies the accounts,
  and the receiver refuses them unless they hash to what the DAO voted on — otherwise whoever executes
  a proposal chooses which accounts it acts on.
- **A single authority PDA.** Governance acts on Solana programs through one program-derived address,
  which those programs must grant their admin roles to. It is the Solana equivalent of the Arbitrum
  timelock holding roles, and the role migration runbook is extended to cover it.

**What a forged VAA can do, with these in place:** schedule an action that waits out the timelock in
public, where the pause authority can stop it, bounded by the value caps. That is the risk the spec
accepts. Without them, a guardian compromise executes immediately.

### 2.10 One direction only — *proposed*

Messages flow Arbitrum → Solana and never back. A proposal that executes on Solana is not reported to
Arbitrum over the bridge; the backend indexes both chains and correlates the two by the VAA's sequence
number.

The alternative — a return receipt — doubles the bridge surface to let one contract record a result
that the indexer can already show. v0.3's `DISPATCHED` state exists for exactly this: "sent, outcome
not known on this chain."

### 2.11 How the bridge is tested — *proposed, with a gap stated*

Locally, Wormhole's core contracts run on both local chains — Anvil and `solana-test-validator` —
configured with a guardian set of one test key. A test process plays the guardian: it observes the
dispatcher's message and signs the VAA. Everything past signature verification is real. How each side
is obtained was settled by the spike: §6.

**The gap:** real guardians are never exercised. That requires deploying to Arbitrum Sepolia and Solana
devnet, and the project deploys nowhere. v2.0's release notes will say so, and name the trigger.

## 3. Build order

Each step ends green and reviewable.

0. **Spike — a local Wormhole round trip.** Publish a message on Anvil, sign it with a test guardian,
   and have it verified against the core bridge's guardian set on `solana-test-validator`. **Done: §6.** First, because it is the step
   that can fail, and everything in §2.9 assumes it works — the same reason browser proving was spiked
   before any UI was built on it.
1. Make transaction identity chain-canonical (§2.5); add the chain id registry and its uniqueness test
   (§2.6). **Done: §7.** Toolchain pinning moved to step 2, where there is a workspace to pin.
2. The Solana vault program, with unit tests and an IDL drift check.
3. The Solana chain client and indexer handlers, and an end-to-end test against `solana-test-validator`:
   a deposit indexed and served beside an Arbitrum one.
4. The Solana oracle program, node signing, and per-chain aggregation and slashing.
5. The Arbitrum dispatcher: the timelock's non-local branch, which today reverts
   `CrossChainDispatchUnavailable`, publishes to Wormhole.
6. The Solana governance receiver, and an end-to-end test of a proposal passed on Arbitrum executing on
   Solana — and of each §2.9 control refusing what it should.
7. The UI across both chains.
8. Release notes; tag `v2.0.0`.

## 4. Invariants

- No price and no vault balance crosses the bridge.
- A VAA from any emitter other than the Arbitrum dispatcher is rejected.
- No inbound message executes before its timelock, while paused, or beyond the value caps.
- A VAA executes at most once.
- A proposal executes only against the accounts the DAO voted on.
- No indexed event is lost to log truncation.
- No two configured chains share a `chain_id`.
- Nothing is indexed from Solana below `finalized`.

## 5. Risk register

| Risk | Severity | Mitigation | Residual |
|---|---|---|---|
| Guardian set compromise forges a governance message | High | §2.9: timelock, pause, caps, emitter allowlist | An action within the caps that nobody pauses in time |
| Real guardians never exercised before release | Medium | §2.11 local round trip | The production verification path is untested |
| Events lost to RPC log truncation | Medium | §2.4 `emit_cpi!` | — |
| Indexing Solana blocks that are later dropped | Medium | §2.7 `finalized` commitment | Slower indexing |
| Two chains sharing a `chain_id` | Medium | §2.6 uniqueness test | A future chain added without running it |
| A 64-byte transaction id truncated or rejected | Medium | §2.5 chain-canonical encoding | — |
| The zk gate exists on one chain only | Low | §2.2, recorded in `DEFERRED.md` | Private actions are Arbitrum-only |

**Scale.** This is larger than v0.1 through v1.3 combined: a second contract language and program model,
a second chain client, and a bridge whose trust assumption becomes part of the protocol's security.

## 6. Spike results (step 0)

The round trip works. A message published through Wormhole's core contract on Anvil was signed by a
test guardian, and an Anchor program on `solana-test-validator` accepted it after verification against a
guardian set created by Wormhole's own Solana core bridge. Three forgeries were rejected:

| Delivered | Result |
|---|---|
| The genuine VAA | Accepted; sequence and payload read from the verified body |
| Signed by a key outside the guardian set | Rejected by the shim: signature does not recover the guardian |
| Payload altered after signing | Rejected by the shim: signature does not recover the guardian |
| Validly signed, but from a different emitter | Rejected by the receiver's allowlist |

The spike code was throwaway and is not committed; what it established changes the plan in five ways.

**1. The Solana core bridge cannot be built from source with our toolchain.** It pins Solana 1.10.31 and
a 2022 nightly compiler. Instead, the programs Wormhole has deployed on Solana mainnet are loaded into
the local validator at their mainnet addresses:

| Program | Address | SHA-256 of the dumped binary |
|---|---|---|
| Core bridge | `worm2ZoG2kUd4vFXhvjh93UUH596ayRfgQ2MgjNMTth` | `a9ce97f30d37f905ee55c7e72d3777c9fc6c5108a501d9e790526a9ffb3a5af1` |
| Verify-VAA shim | `EFaNWErqAtVWufdNb7yofSHHfWFos843DFpu4JBw24at` | `6b1e2db28fd49e2111ff2af33dd24d9580b454e2771007754f6e29decb798226` |

Proposed: both binaries are committed with those hashes, checked in CI, so no test depends on a
mainnet RPC being reachable. They are the programs real messages would meet, which a local rebuild
would not be. Wormhole publishes verifiable builds for both, which is the route to confirming the
hashes against source.

**2. VAAs are verified through Wormhole's verify-VAA shim, not the core bridge's `post_vaa`.** The
receiver passes the VAA's digest to the shim by CPI; the shim checks the signatures against the core
bridge's guardian set account — its address, its expiry, quorum, and strictly increasing guardian
indices. The older route leaves two accounts on chain for every message, permanently. **The shim
verifies signatures only.** The emitter, replay, timelock, pause, and caps of §2.9 are the receiver's,
and the spike shows the emitter check is what stopped a validly signed message from the wrong sender.

**3. Program ids are per cluster.** The mainnet binaries have their own ids compiled in, and the shim
hard-codes the core bridge's. The receiver's shim and core bridge addresses therefore come from a build
feature per cluster, and a test asserts the local build uses the ids of the binaries it loads.

**4. The EVM core contract is test infrastructure, and needs its own Foundry project.** It compiled
unmodified under our `solc 0.8.28` (upstream pins 0.8.4), but it imports OpenZeppelin 4, and ours is
OpenZeppelin 5. It lives apart from `contracts/src`, is deployed only to Anvil, and nothing of ours
inherits from it; the dispatcher calls it through a one-function interface.

**5. Anchor 1.1.2 on Solana 3.x no longer exposes hashing under `solana_program`.** Keccak and SHA-256
come from the `solana-keccak-hasher` and `solana-sha256-hasher` crates, pinned with the toolchain.

The test guardian is Wormhole's own published development key. It is safe only because no guardian set
outside the local validators contains it.

## 7. Step 1 results

**Transaction identity.** `chain.Event.TxHash` is now the chain client's canonical string, produced by
the EVM client as lowercase `0x`-hex exactly as before, so no stored value changes and no migration is
needed. The indexer's own hex encoder is gone: handlers store what the client gives them.

Two things are refused that were not before. An event with an empty transaction identifier stops the
batch rather than being indexed — `(chain_id, tx_hash, log_index)` is an event's identity, and with
`ON CONFLICT DO NOTHING`, every such event in a transaction after the first would be silently dropped.
And an architecture test fails if any shared Go type declares a transaction identifier as a fixed-width
array; chain implementations under `internal/chain/<vm>/` are exempt, since that is where the native
width belongs. Both were confirmed to fail when broken.

**Chain ids.** `pkg/types/chain.go` is the only place an id is assigned:

| Chain | VM | Id |
|---|---|---|
| `arbitrum-one` | EVM | 42161 |
| `arbitrum-sepolia` | EVM | 421614 |
| `anvil` | EVM | 31337 |
| `solana-mainnet` | SVM | `2^62 + 1` |
| `solana-devnet` | SVM | `2^62 + 2` |
| `solana-localnet` | SVM | `2^62 + 3` |

Tests assert no two chains share an id or name, EVM ids lie below `2^62`, and every other id lies above
it. Every service now refuses to start with an id not in the registry. Before, any positive number was
accepted, and a mistyped `CHAIN_ID` would not have failed: it would have indexed into rows no other
service reads.
