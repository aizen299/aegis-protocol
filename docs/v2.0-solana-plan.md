# v2.0 — Solana

Phase 2 of `docs/project-spec.md`: a second chain. Solana is the confirmed target, and the spec's §7 is
binding on how it is added — read it first. This plan records the decisions taken at the start of
Phase 2, the decisions that follow from them, and the order in which the work is built.

**Nothing here is built yet.** §2.4 onward are proposals that need sign-off before code.

---

## 1. What the spec already decides

Three constraints are not open, and every decision below is made inside them:

- **Oracle prices do not cross chains.** Each chain runs its own oracle node set, with its own staking
  and slashing. Routing prices over a bridge would replace trust-minimised aggregation with the
  bridge's trust assumption, which is strictly weaker.
- **Vault accounting does not cross chains.** Each chain's vault has its own TVL and share price. A
  user with positions on two chains holds two positions. Unified accounting would let a bridge failure
  corrupt solvency on the healthy chain too.
- **Governance is the only sanctioned cross-chain message.** One DAO, on Arbitrum, whose passed
  proposals can execute on Solana. The receiving side must impose a timelock on inbound messages, be
  pausable, and enforce per-message and rolling value caps.

## 2. Decisions

### 2.1 Messaging layer: Wormhole — *decided*

Chosen for the specific pairing. Solana↔EVM is the route Wormhole was built around and has carried
longest, with the deepest tooling on both sides; for the alternatives, Solana is one destination among
many. Its trust assumption is also legible: a fixed guardian set, whose signatures on a message —
a VAA — are what the receiving chain verifies.

**The counterpoint, held rather than dismissed:** Wormhole is the option that was exploited, on its
Solana side, for about $320M in 2022. The flaw was in signature verification and has been fixed. What
this plan takes from it is not a reason to choose differently but a requirement on the receiver:
**a forged VAA must be survivable.** Every control in §2.9 exists because the guardian set is a single
point of trust, and the design assumes it can fail.

### 2.2 Modules on Solana: vault, oracle, governance receiver — *decided*

**The zk gate is deferred past v2.0.** Its verifier is generated for Solidity by the pinned
Barretenberg toolchain, and there is no equivalent generated verifier for Solana programs. Bringing it
over means a different proof system or a hand-written verifier, and the project's rule is that
verifiers are generated, never hand-written. Recorded in `DEFERRED.md` when this plan is approved.

### 2.3 Build order — *decided as "all three"; sequenced here*

All three modules ship in v2.0. The order below follows dependency, not preference, and can be changed:

1. **Vault first.** It proves the whole Solana path — an Anchor program, a second chain client, the
   indexer, the API, the UI — with no bridge involved.
2. **Oracle second.** The largest program, with no bridge dependency either.
3. **Governance receiver last.** The only piece that touches Wormhole, so it is built on top of a
   Solana path that already works rather than alongside one that does not.

### 2.4 Anchor, and events recorded as CPI data rather than logs — *decided / proposed*

Anchor is decided. It generates an IDL the indexer decodes from — the same role ABIs play today — so
the existing drift-check pattern carries over, and its account constraints rule out the missing
signer and owner checks behind most Solana exploits.

**Proposed: events are emitted with `emit_cpi!`, not `emit!`.** `emit!` writes events to program logs,
and Solana RPC nodes truncate transaction logs past a size limit. An event dropped from a log is an
event the indexer never sees — a deposit that silently never reaches Postgres. `emit_cpi!` records the
event as the data of a self-invocation, retrieved from the transaction's inner instructions, which are
not truncated.

### 2.5 Transaction identity is not 32 bytes — *proposed; a gap in Phase 1*

The spec's Phase 1 constraints required account identity to be 32 bytes. They did not cover
transaction identity. `chain.Event.TxHash` is `[32]byte`, and every indexed row is identified by
`(chain_id, tx_hash, log_index)` — but a Solana transaction is identified by its signature, which is
**64 bytes**.

The database is already safe: every `tx_hash` column is `TEXT` with no length or format constraint. The
assumption lives in the Go type and in the indexer's hex encoding.

**Proposed:** `TxHash` becomes the chain's canonical string form, produced by the chain client the way
`EncodeIdentity` already produces account identities — `0x`-hex for EVM, base58 for Solana. No
migration. An architecture test asserts no shared type fixes a transaction identifier's width.

### 2.6 A chain id for Solana — *proposed*

Every chain-derived row carries a `BIGINT chain_id`. EVM chains have numeric ids; Solana clusters do not.

**Proposed:** each Solana cluster is assigned a stable `int64` in a single registry in the backend,
recorded in this plan when step 1 lands, with a test that fails if any two chains share an id.

*Corrected in step 1:* Phase 1 had already reserved a range for this — ids from `2^62` up are never
EVM chain ids — so assignments come from that range rather than relying on the test alone.

### 2.7 Finality — *proposed*

The indexer reads Solana at `finalized` commitment. Solana's equivalent of the EVM confirmation window
is not a slot count but a commitment level; indexing at `confirmed` would index blocks that can still
be dropped. The Solana client reports a confirmation depth of zero and treats the finalized slot as the
safe head.

### 2.8 Oracle signatures on Solana — *proposed*

Nodes sign submissions with ed25519, verified on chain through Solana's native Ed25519 program. The
signed message carries the program id, the cluster's chain id, the round, and the node's nonce — the
same replay protection the EVM side gets from EIP-712's chain id and contract address, so a signature
for one cluster or program cannot be replayed against another.

Slashing keeps the existing key policy: the slasher key resolves through the same environment-declared
secret source as the EVM one, and staging never falls back to a development key.

### 2.9 The governance receiver — *binding requirements, plus proposals*

Required by the spec: an execution timelock, a pause authority, and per-message and rolling value
caps. Proposed in addition:

- **An emitter allowlist of exactly one.** A VAA is accepted only if emitted by the Arbitrum dispatcher
  contract on Arbitrum's Wormhole chain id. Any other emitter is rejected before anything else is read.
- **Replay protection.** Each accepted VAA's hash is recorded in an account; a second submission of the
  same VAA fails.
- **An instruction payload bound to its accounts.** The payload names the target program, the
  instruction data, and a hash of the account list. The executing transaction supplies the accounts,
  and the receiver refuses them unless they hash to what the DAO voted on — otherwise whoever executes
  a proposal chooses which accounts it acts on.
- **A single authority PDA.** Governance acts on Solana programs through one program-derived address,
  which those programs must grant their admin roles to. It is the Solana equivalent of the Arbitrum
  timelock holding roles, and the role migration runbook is extended to cover it.

**What a forged VAA can do, with these in place:** schedule an action that waits out the timelock in
public, where the pause authority can stop it, bounded by the value caps. That is the risk the spec
accepts. Without them, a guardian compromise executes immediately.

### 2.10 One direction only — *proposed*

Messages flow Arbitrum → Solana and never back. A proposal that executes on Solana is not reported to
Arbitrum over the bridge; the backend indexes both chains and correlates the two by the VAA's sequence
number.

The alternative — a return receipt — doubles the bridge surface to let one contract record a result
that the indexer can already show. v0.3's `DISPATCHED` state exists for exactly this: "sent, outcome
not known on this chain."

### 2.11 How the bridge is tested — *proposed, with a gap stated*

Locally, Wormhole's core contracts run on both local chains — Anvil and `solana-test-validator` —
configured with a guardian set of one test key. A test process plays the guardian: it observes the
dispatcher's message and signs the VAA. Everything past signature verification is real. How each side
is obtained was settled by the spike: §6.

**The gap:** real guardians are never exercised. That requires deploying to Arbitrum Sepolia and Solana
devnet, and the project deploys nowhere. v2.0's release notes will say so, and name the trigger.

## 3. Build order

Each step ends green and reviewable.

0. **Spike — a local Wormhole round trip.** Publish a message on Anvil, sign it with a test guardian,
   and have it verified against the core bridge's guardian set on `solana-test-validator`. **Done: §6.** First, because it is the step
   that can fail, and everything in §2.9 assumes it works — the same reason browser proving was spiked
   before any UI was built on it.
1. Make transaction identity chain-canonical (§2.5); add the chain id registry and its uniqueness test
   (§2.6). **Done: §7.** Toolchain pinning moved to step 2, where there is a workspace to pin.
2. The Solana vault program, with unit tests and an IDL drift check. **Done: §9.**
3. The Solana chain client and indexer handlers, and an end-to-end test against `solana-test-validator`:
   a deposit indexed and served beside an Arbitrum one. **Done: §11.**
4. The Solana oracle program, node signing, and per-chain aggregation and slashing.
5. The Arbitrum dispatcher: the timelock's non-local branch, which today reverts
   `CrossChainDispatchUnavailable`, publishes to Wormhole.
6. The Solana governance receiver, and an end-to-end test of a proposal passed on Arbitrum executing on
   Solana — and of each §2.9 control refusing what it should.
7. The UI across both chains.
8. Release notes; tag `v2.0.0`.

## 4. Invariants

- No price and no vault balance crosses the bridge.
- A VAA from any emitter other than the Arbitrum dispatcher is rejected.
- No inbound message executes before its timelock, while paused, or beyond the value caps.
- A VAA executes at most once.
- A proposal executes only against the accounts the DAO voted on.
- No indexed event is lost to log truncation.
- No two configured chains share a `chain_id`.
- Nothing is indexed from Solana below `finalized`.

## 5. Risk register

| Risk | Severity | Mitigation | Residual |
|---|---|---|---|
| Guardian set compromise forges a governance message | High | §2.9: timelock, pause, caps, emitter allowlist | An action within the caps that nobody pauses in time |
| Real guardians never exercised before release | Medium | §2.11 local round trip | The production verification path is untested |
| Events lost to RPC log truncation | Medium | §2.4 `emit_cpi!` | — |
| Indexing Solana blocks that are later dropped | Medium | §2.7 `finalized` commitment | Slower indexing |
| Two chains sharing a `chain_id` | Medium | §2.6 uniqueness test | A future chain added without running it |
| A 64-byte transaction id truncated or rejected | Medium | §2.5 chain-canonical encoding | — |
| The zk gate exists on one chain only | Low | §2.2, recorded in `DEFERRED.md` | Private actions are Arbitrum-only |

**Scale.** This is larger than v0.1 through v1.3 combined: a second contract language and program model,
a second chain client, and a bridge whose trust assumption becomes part of the protocol's security.

## 6. Spike results (step 0)

The round trip works. A message published through Wormhole's core contract on Anvil was signed by a
test guardian, and an Anchor program on `solana-test-validator` accepted it after verification against a
guardian set created by Wormhole's own Solana core bridge. Three forgeries were rejected:

| Delivered | Result |
|---|---|
| The genuine VAA | Accepted; sequence and payload read from the verified body |
| Signed by a key outside the guardian set | Rejected by the shim: signature does not recover the guardian |
| Payload altered after signing | Rejected by the shim: signature does not recover the guardian |
| Validly signed, but from a different emitter | Rejected by the receiver's allowlist |

The spike code was throwaway and is not committed; what it established changes the plan in five ways.

**1. The Solana core bridge cannot be built from source with our toolchain.** It pins Solana 1.10.31 and
a 2022 nightly compiler. Instead, the programs Wormhole has deployed on Solana mainnet are loaded into
the local validator at their mainnet addresses:

| Program | Address | SHA-256 of the dumped binary |
|---|---|---|
| Core bridge | `worm2ZoG2kUd4vFXhvjh93UUH596ayRfgQ2MgjNMTth` | `a9ce97f30d37f905ee55c7e72d3777c9fc6c5108a501d9e790526a9ffb3a5af1` |
| Verify-VAA shim | `EFaNWErqAtVWufdNb7yofSHHfWFos843DFpu4JBw24at` | `6b1e2db28fd49e2111ff2af33dd24d9580b454e2771007754f6e29decb798226` |

Proposed: both binaries are committed with those hashes, checked in CI, so no test depends on a
mainnet RPC being reachable. They are the programs real messages would meet, which a local rebuild
would not be. Wormhole publishes verifiable builds for both, which is the route to confirming the
hashes against source.

**2. VAAs are verified through Wormhole's verify-VAA shim, not the core bridge's `post_vaa`.** The
receiver passes the VAA's digest to the shim by CPI; the shim checks the signatures against the core
bridge's guardian set account — its address, its expiry, quorum, and strictly increasing guardian
indices. The older route leaves two accounts on chain for every message, permanently. **The shim
verifies signatures only.** The emitter, replay, timelock, pause, and caps of §2.9 are the receiver's,
and the spike shows the emitter check is what stopped a validly signed message from the wrong sender.

**3. Program ids are per cluster.** The mainnet binaries have their own ids compiled in, and the shim
hard-codes the core bridge's. The receiver's shim and core bridge addresses therefore come from a build
feature per cluster, and a test asserts the local build uses the ids of the binaries it loads.

**4. The EVM core contract is test infrastructure, and needs its own Foundry project.** It compiled
unmodified under our `solc 0.8.28` (upstream pins 0.8.4), but it imports OpenZeppelin 4, and ours is
OpenZeppelin 5. It lives apart from `contracts/src`, is deployed only to Anvil, and nothing of ours
inherits from it; the dispatcher calls it through a one-function interface.

**5. Anchor 1.1.2 on Solana 3.x no longer exposes hashing under `solana_program`.** Keccak and SHA-256
come from the `solana-keccak-hasher` and `solana-sha256-hasher` crates, pinned with the toolchain.

The test guardian is Wormhole's own published development key. It is safe only because no guardian set
outside the local validators contains it.

## 7. Step 1 results

**Transaction identity.** `chain.Event.TxHash` is now the chain client's canonical string, produced by
the EVM client as lowercase `0x`-hex exactly as before, so no stored value changes and no migration is
needed. The indexer's own hex encoder is gone: handlers store what the client gives them.

Two things are refused that were not before. An event with an empty transaction identifier stops the
batch rather than being indexed — `(chain_id, tx_hash, log_index)` is an event's identity, and with
`ON CONFLICT DO NOTHING`, every such event in a transaction after the first would be silently dropped.
And an architecture test fails if any shared Go type declares a transaction identifier as a fixed-width
array; chain implementations under `internal/chain/<vm>/` are exempt, since that is where the native
width belongs. Both were confirmed to fail when broken.

**Chain ids.** `pkg/types/chain.go` is the only place an id is assigned:

| Chain | VM | Id |
|---|---|---|
| `arbitrum-one` | EVM | 42161 |
| `arbitrum-sepolia` | EVM | 421614 |
| `anvil` | EVM | 31337 |
| `solana-mainnet` | SVM | `2^62 + 1` |
| `solana-devnet` | SVM | `2^62 + 2` |
| `solana-localnet` | SVM | `2^62 + 3` |

Tests assert no two chains share an id or name, EVM ids lie below `2^62`, and every other id lies above
it. Every service now refuses to start with an id not in the registry. Before, any positive number was
accepted, and a mistyped `CHAIN_ID` would not have failed: it would have indexed into rows no other
service reads.

## 8. Step 2 design — the Solana vault (*proposed*)

The Solana vault matches the Arbitrum vault's behaviour: the same exchange-rate maths, slippage floors,
caps, and pause controls, and events carrying the same fields. It is rewritten for Solana's account
model rather than translated line by line, per §1. Eight decisions follow.

**8.1 No yield strategy.** The Arbitrum vault has a strategy interface, but no strategy ships. On
Solana, a strategy is a CPI into another protocol, whose account list is that protocol's. Building the
hook with nothing to test it against would be designing blind. The Solana vault holds idle assets only;
recorded in `DEFERRED.md`.

**8.2 Shares are a ledger, not a token.** Each holder has a position account — a PDA of
`["position", vault, owner]` — holding their shares, and shares cannot be transferred. This matches the
Arbitrum vault, whose shares are internal balances and not an ERC-20. An SPL share mint would add a
second token and a transfer surface, and nothing in the protocol needs either.

**8.3 Classic SPL Token only; Token-2022 mints refused.** A Token-2022 mint can charge a transfer fee or
run a transfer hook, so a transfer of `amount` may not deliver `amount`. The Arbitrum vault handles
this by measuring its balance before and after. On Solana the simpler and safer rule is to refuse such
mints when a vault is created.

**8.4 The virtual-shares defence, as on Arbitrum.** An offset of 3 — `10^3` virtual shares and 1
virtual asset — against the first-depositor inflation attack. Asset amounts are `u64`, as SPL amounts
are. Shares are `u128`, because an offset of 3 lets a full `u64` deposit mint more than `u64` shares.
All conversions go through `u128` with checked arithmetic, and rounding always favours the vault.

**8.5 Roles are pubkeys in a config account.** Anchor has no `AccessControl`. The config account holds
`admin`, `manager`, and `pauser`. The admin changes hands in two steps, propose then accept, so a
mistyped key cannot orphan the vault. The mapping to Arbitrum:

| Arbitrum | Solana |
|---|---|
| `DEFAULT_ADMIN_ROLE` | `admin`: sets roles, freezes withdrawals |
| `VAULT_MANAGER_ROLE` | `manager`: deposit cap, minimum deposit |
| `PAUSER_ROLE` | `pauser`: pauses and unpauses deposits |
| `UPGRADER_ROLE` | The program's upgrade authority |

In step 6, `admin` passes to the governance authority PDA of §2.9.

**8.6 Only the upgrade authority can create a vault.** On Solana, an initialize instruction anyone can
call is a known exploit: an attacker creates the vault first and names themselves admin. Creation
requires the program's upgrade authority to sign. One vault exists per asset, at
`["vault", mint]`.

**8.7 Account layouts are append-only, and checked.** Solana has no storage-layout check. Each account
carries a version byte and reserved padding, and a committed baseline of every account's layout,
generated from the IDL, fails CI on any change that is not an append. This is the counterpart of
`make contracts-layout-check`.

**8.8 Events via `emit_cpi!`, same fields as Arbitrum.** `Deposited` and `Withdrawn` carry the same
fields as their Arbitrum counterparts, so the indexer maps both into the existing tables. A holder can
close a position that has reached zero shares, to reclaim its rent.

**Tests.** Unit tests of the maths — rounding, the inflation attack, bounds. Instruction tests against
a local validator, covering each refusal: a wrong signer, a Token-2022 mint, over the cap, below the
minimum, a slippage floor, deposits while paused, withdrawals while frozen, a second vault for the same
mint. Plus an IDL drift check and the layout baseline.

## 9. Step 2 results

`solana/programs/aegis_vault` implements §8, and CI (`Solana CI`) checks every part of it: the toolchain
pins, formatting and clippy, 33 tests, the IDL against the committed copy in `solana/idl/`, and account
layouts against `solana/layouts/`.

**Instructions.** `initialize_vault`, `deposit`, `withdraw`, `close_position`, `set_deposit_cap`,
`set_min_deposit`, `set_paused`, `set_withdrawals_frozen`, `set_role`, `propose_admin`, `accept_admin`.
Every one emits its event with `emit_cpi!`. `Deposited` and `Withdrawn` carry `user`, `asset`, `amount`,
`shares`, the same fields as on Arbitrum; a test asserts the event is in the inner instructions and not
in the logs.

**Tests.** 8 unit tests of the maths and 25 instruction tests. The instruction tests run the compiled
program in LiteSVM, an in-process Solana runtime, rather than the local validator §8 named. It runs the
same program binary with the real SPL Token program, fast enough to cover every refusal. The validator
is used from step 3, where the indexer needs a real RPC.

Every guard was then removed in turn to confirm a test fails without it. All fourteen were caught:
the upgrade-authority check, the program-data binding, pause, both slippage floors, freeze, cap,
minimum, insufficient shares, the manager check, admin acceptance, closing a non-empty position, and
setting the admin directly. The first run caught all but one — nothing tested an attacker passing the
program data of a program *they* control — and that test was added before this was recorded.

**What building it found, beyond §8:**

- **An overflow that would have locked a withdrawal.** A position holding a full `u64` deposit's shares
  (`u64::MAX × 1000`) overflows `u128` when multiplied by the vault's balance. The first fallback
  still refused it. The maths now does exact 256-bit multiply-then-divide, cross-checked against plain
  arithmetic on 20,000 generated inputs. A unit test found it. An expected value in that test was
  first typed rather than computed, and was wrong; it now comes from an independent calculation.
- **`Option<Pubkey>` has no fixed layout.** Borsh stores `None` in 1 byte and `Some` in 33, so every
  field after `pending_admin` would have moved when an admin was proposed. The layout check refuses
  variable-size fields outright, and `pending_admin` is a `Pubkey` whose zero value means none.
- **The zero key is refused for every role and as a deposit receiver.** It is how "none" is stored, and
  nobody holds its private key, so a role or position given to it is lost. The Arbitrum vault refuses
  `address(0)` the same way.
- **Anchor 1.x already refuses the same mutable account twice.** A guard against withdrawing into the
  vault's own token account was redundant and was removed. The test stays, so the refusal cannot
  disappear in a framework upgrade unnoticed.

**Toolchain.** Anchor 1.1.2 and Solana 3.1.10, pinned in `solana/Anchor.toml` and checked by
`make solana-toolchain-check`. Programs compile with the Rust that ships in Solana's platform tools
(1.89). The host toolchain is pinned to 1.94 in `solana/rust-toolchain.toml`, because the in-process
runtime the tests use needs it.

**The program keypair is not committed.** The program id is fixed by `declare_id!` and carried into the
IDL. A clean checkout's `anchor build` generates a new keypair and warns that it does not match; the
binary and IDL are unaffected. A deploy key is created when there is a deployment, not before.

## 10. Step 3 design — indexing Solana (*proposed*)

Step 3 puts a Solana deposit into Postgres and serves it from the API, next to Arbitrum's. The shared
tables need no change, since Phase 1 made them chain-neutral. The work is a second chain client, a
change in how the vault handler finds its vault, and a way for the API to serve more than one chain.

**10.1 The client talks JSON-RPC directly, without a Solana SDK.** It needs five calls:
`getSlot`, `getSignaturesForAddress`, `getTransaction`, `getBlockTime`, and `getAccountInfo`. Decoding
is driven by the committed IDL, the way the EVM client decodes from committed ABIs. The only new
dependency is a base58 package. A full SDK would bring a large dependency tree for those five calls.

**10.2 Transactions are found by program address, not by walking slots.** Solana has no log filter.
Reading every slot means about 216,000 blocks a day, nearly all empty for us. Instead the client pages
`getSignaturesForAddress` for the vault program back to the batch's first slot, then fetches each
transaction. The cursor stays "last slot processed", and the head is the `finalized` slot (§2.7).

This relies on the RPC node keeping transaction history back to the cursor. A pruning node would
silently return nothing for old slots, so the client refuses to index a range older than the node's
oldest available slot, rather than reading an empty answer as "no events".

**10.3 Only events the program itself emitted are accepted.** An event is an inner instruction to the
vault program, whose first account is the program's event authority and whose data starts with
Anchor's event tag. Four things are refused:
- **Failed transactions.** They can still report inner instructions that ran before the failure.
- **Top-level instructions.** An event must be a CPI from the program.
- **Instructions to any other program.**
- **Any tag the IDL does not name.**

`log_index` is the event's position among that transaction's accepted events, so
`(chain_id, signature, log_index)` stays unique and stable across replays.

**10.4 On-chain state says which vault an event belongs to.** On Arbitrum, the contract that emitted an
event is the vault. On Solana, one program holds a vault per mint, at `["vault", mint]`. The vault
handler asks a chain-specific locator which vault an event's asset belongs to, instead of assuming the
emitter is the vault. The Solana locator derives the address, reads the account, and refuses if the
account's mint is not the event's asset.

**10.5 The share offset is stored in the vault account.** Arbitrum's vault exposes its offset through a
view function, and the indexer reads it rather than assuming 3. Solana has no view calls. A constant in
the IDL would describe the IDL, not the deployed binary. So `share_offset` becomes a field of the vault
account, taken from `reserved` by the layout rule. The vault program is unreleased, so this also
exercises the layout check on its first real change.

**10.6 Asset metadata is decimals only.** An SPL mint stores its decimals; name and symbol live in an
optional Metaplex account that many mints lack. The `symbol` and `name` columns are already nullable,
and are left empty rather than read from a second program the protocol does not otherwise depend on.

**10.7 One indexer process per chain, chosen by its chain id's VM.** Unchanged from Phase 1: `CHAIN_ID`
names a registry entry, and its VM decides which client is built. Contract addresses are given in that
chain's own encoding.

**10.8 The API serves every configured chain, and never guesses one.** Today each API process serves
one chain. Proposed: routes take a `chain` query parameter naming a registry entry, such as
`chain=solana-localnet`. The API accepts only the chains it is configured for (`API_CHAINS`), and
decodes addresses with that chain's encoding. Encoding needs no RPC connection, so the API stops
opening one. When `chain` is absent, the one configured chain is used if there is exactly one; with
more than one, the request is refused. The frontend is unaffected until it sends the parameter in step 7.

**10.9 The end-to-end test runs a real validator.** `scripts/e2e.sh` also starts `solana-test-validator`,
with the vault program at its declared id and the test key as upgrade authority. The test runs a
Solana indexer against it and an Arbitrum indexer against Anvil. A deposit on each chain must come back
from the API under its own `chain`, with the right decimals and share scale. The test also checks that
a failed Solana transaction is not indexed. Both chains index into the same database. E2E CI installs
the Solana toolchain the same way Solana CI does.

## 11. Step 3 results

A Solana deposit is indexed into the same Postgres as Arbitrum's and served by one API under its own
`chain`. The end-to-end test runs both chains for real: Anvil, and `solana-test-validator` with the
vault program at its declared id.

**What was built.**

- **`internal/chain/svm`** — the Solana client. It makes six JSON-RPC calls (the five in §10.1 plus
  `getGenesisHash`), decodes events and accounts from the IDL, and derives PDAs. Base58 and PDA
  derivation match `solana find-program-derived-address`.
- **`svm.VaultLocator` and `evm.VaultReader`** — both implement the vault handler's new `VaultLocator`.
  Rows carry the vault the locator found, not the emitter.
- **`cmd/indexer`** — builds the client that `CHAIN_ID`'s VM calls for. On Solana it refuses any
  configured oracle, governance, or zk contract, and refuses a `CONTRACT_VAULT_ENGINE` that is not the
  program the embedded IDL describes.
- **The API** — resolves `chain` per request against `API_CHAINS`, defaulting to `CHAIN_ID`'s chain
  when unset. A module a chain lacks answers `404 MODULE_NOT_ON_CHAIN`. The API opens no RPC
  connection.
- **The vault account** gains `share_offset`, carved from `reserved`. The layout check accepted the
  change as legal before the baseline was re-recorded, and re-recording it locks the new field.
- **`backend/pkg/contracts/solvault`** — embeds the IDL. `make backend-idl-check` runs in Backend CI.
- **`scripts/solana-validator.sh`** — starts the validator for both `make e2e` and E2E CI.

**Tests.** 17 unit tests in `internal/chain/svm`, with each client refusal mutation-checked: removing the guard
fails its test for failed transactions, the event authority, pruned ranges, filter-independent log
indexes, mint and vault ownership, the genesis pin, ordering, and the range end. 5 API tests for
chain resolution. 2 config tests. 1 vault handler test for rows carrying the located vault. One
end-to-end test, which:

- deposits on Anvil and on Solana;
- sends a Solana transaction whose first deposit succeeds and emits its event, and whose second
  fails, so the whole transaction fails;
- indexes both chains, and asserts exactly one Solana deposit, carrying its 64-byte signature, the
  vault PDA, six decimals, and share decimals of 9;
- serves both positions through one API, and refuses a Solana address on `anvil` and a request that
  names no chain;
- replays the Solana range with a second indexer and finds no duplicate.

**What building it found:**

- **Failed transactions really do report the inner instructions that ran before the failure,
  including our event data.** So skipping failed transactions is not defensive tidiness; without it,
  a rolled-back deposit is indexed. The end-to-end test checks the validator reports the event, so the
  exclusion cannot pass vacuously. It also fails, with two deposits, when the skip is removed.
- **`log_index` has to be counted before filtering.** Counted after, the same event would get a
  different index depending on which events a caller asked for, and replaying with a different filter
  would insert it again. The unit test mutation confirms it.
- **The SPL Token program id was mistyped at first.** It failed at package init, not silently,
  because `MustIdentity` refuses a non-canonical key.
- **A test vector was wrong, not the decoder.** A base58 key with its last character removed can
  still be a valid, different 32-byte key. It was replaced with lengths that cannot decode to 32 bytes.

**Not exercised.** The `indexer` and `api` binaries were not run against the validator. The
end-to-end test drives the same client, handler, indexer, and server in-process, as the Arbitrum tests
do. The Docker Compose stack still serves Arbitrum only.

## 12. Step 4 design — the Solana oracle (*proposed*)

The Solana oracle has the same behaviour as Arbitrum's: staked nodes; rounds that freeze their eligible
set when they open; signed submissions; a quorum measured against that frozen set; a median; slashing
capped per round; and missed-round penalties judged off chain. Per §1, it shares nothing with Arbitrum:
its own nodes, its own stake, its own prices.

It is the largest step in the plan, so it lands as three commits, each ending green:

- **4a** — the program, and its tests.
- **4b** — the node submitting from Go, and indexing into the existing oracle tables, with an
  end-to-end round on the validator.
- **4c** — the aggregator verifying signatures and slashing on Solana, including missed rounds,
  end to end.

**12.1 One program, not two.** On Arbitrum, staking and rounds are separate contracts, each with its
own roles. On Solana, a second program would put a CPI and a cross-program account check on every
submission's eligibility test, for no isolation the roles do not already give. `aegis_oracle` holds:

| Account | Address | Holds |
|---|---|---|
| Config | `["config"]` | roles, parameters, `node_set_version`, active node count, next round id, stake mint |
| Node | `["node", node]` | stake, pending unstake, `activated_at_version`, active |
| Feed | `["feed", feed_id]` | decimals, current round, last settled value and its time |
| Round | `["round", round_id]` | state, deadline, frozen version and eligible count, submitted values |
| Submission | `["submission", round, node]` | exists only to make a second submission fail |
| Slash record | `["slash", round, node]` | exists only to make a second slash for that round fail |

Eligibility is the Arbitrum rule unchanged: active, with `activated_at_version <=` the round's frozen
version.

**12.2 A hard cap of 32 nodes.** A Round stores its submitted values in a fixed `[u128; 32]`, so the
account keeps a fixed layout (§8.7) and the median's sort is bounded by a constant. `max_nodes` is a
parameter up to 32. This also closes, on Solana, the Low finding that `setMaxNodes` on Arbitrum has no
ceiling.

**12.3 Submissions are signed attestations, verified through Solana's Ed25519 program.** As on Arbitrum,
the node sends the transaction and also signs an attestation the aggregator can verify on its own. The
signed message is:

`"aegis-oracle-submission-v1" ‖ program id ‖ chain id ‖ round id ‖ feed id ‖ value ‖ node ‖ nonce`

It carries the domain, program, and chain, per §2.8. `submit` requires the instruction before it in the
same transaction to be an Ed25519 verification of exactly those bytes, by the node's key. That check
reads the instructions sysvar, which is where Solana's best-known exploits happened, so it is written to
refuse each of the following, and each gets a test:

- a sysvar account that is not the real instructions sysvar;
- a verification by a program other than Ed25519;
- offsets pointing outside that instruction's own data;
- a different message or key;
- a verification that is not the immediately preceding instruction.

**12.4 Widths follow Solana.** Values are `u128` (18-decimal prices overflow `u64`). Round ids and
nonces are `u64`. Stake is `u64`, as SPL amounts are. The stake token is a classic SPL mint, fixed at
initialization. Token-2022 is refused, as in the vault.

**12.5 Roles.** `admin`, `oracle_manager` (feeds and parameters), `pauser`, and `slasher`, with the
same two-step admin handover as the vault. Only the upgrade authority can initialize. Pause stops
opening rounds and submitting, as on Arbitrum.

**12.6 No `latest_answer`.** `get_value(feed, max_staleness)` returns the last settled value through
return data, and fails if there is none or it is stale. The same rule as `IOracleReader`: a caller
must state how old is too old.

**12.7 Events match Arbitrum's names and fields**, so `internal/indexer`'s oracle handlers and the
missed-round judgement (already chain-neutral) take them unchanged. Where Arbitrum emits a
`bytes32` reason, Solana emits the same 32 bytes.

**12.8 The backend gets Solana implementations of interfaces that already exist**:
- `oraclenode.Chain` — reads the Feed and Round accounts; submits the Ed25519 verification and
  `submit` in one transaction.
- `oracle.SignatureVerifier` — ed25519 over the same message bytes.
- `oracle.Slasher` — the slash instruction, with the slash record's refusal mapped to
  `ErrAlreadySlashed`, so a retry after a crash stays safe as it is on Arbitrum.

Building transactions moves out of the end-to-end harness into `internal/chain/svm`, with unit tests,
since production code now sends them.

Node and slasher keys come through the existing secret providers, with the same no-fallback policy. A
Solana key is accepted only in `solana-keygen`'s JSON form, and anything else fails at startup.

**12.9 Account rent is not reclaimed in v2.0.** Round, submission, and slash-record accounts are never
closed. Closing them safely needs a retention rule — a slash record closed early re-opens a double
slash — and v2.0 has no deployment for rent to matter to. Recorded in `DEFERRED.md`, with the trigger
being any deployment.

## 13. Step 4a results — the oracle program

`solana/programs/aegis_oracle` implements §12.1–§12.7: staking, feeds, rounds, submissions, settlement,
`get_value`, slashing, roles, and parameters. Its IDL and a layout baseline for all six accounts are
committed and checked in CI, alongside the vault's.

**Tests.** 6 unit tests cover the median, quorum, the slash cap, and the attestation check. 22
instruction tests run in LiteSVM against the real Ed25519 program. The attestation tests refuse:

- no verification at all;
- a verification signed by another key;
- a message for a different value, chain, or program;
- a verification that is not the immediately preceding instruction;
- a substituted instructions-sysvar account;
- a verification whose offsets read another instruction's data.

That last one is accepted by the runtime, which is the point: the program must not trust bytes the
runtime verified somewhere else.

25 guards were removed one at a time, each followed by a rebuild. 24 fail a test when removed.

The one that does not is the cap check inside `activate()`. Every caller checks for room first, so no
input can reach it; it stays as defence in depth. The first mutation pass also exposed two gaps, both
now closed: nothing tested opening a round while paused, or a zero round duration.

**What building it found:**

- **The Round account overflowed the stack.** 32 `u128` values put `open_round` past the 4 KB frame
  limit, and every round test failed with an access violation until the large accounts were boxed.
- **The Arbitrum median averages the two middle values for an even count.** The first Solana
  version took the lower one. It now uses the same overflow-safe average, so the same submissions
  settle to the same value on both chains, and in the Go aggregator.
- **Events are emitted in Arbitrum's order.** Registration emits `NodeReactivated` before
  `NodeRegistered`, because activation happens first.
- **ORC-2, on Arbitrum.** `OracleStaking.stake()` and `cancelUnstake()` reactivate a node without
  checking `maxNodes`, and `OracleRounds` declares `_MAX_SUBMISSIONS = 31` but never enforces it.
  Stakers can therefore grow the active set past its cap, and with it the O(n²) settlement sort. A
  throwaway Foundry test reproduced it: with `maxNodes` set to 2, one unstake-then-cancel left 3
  active nodes. `DEFERRED.md` had described the sort as bounded and only a trusted role as able to
  raise the bound.

  **Fixed before 4b.** Every reactivation checks for room, `maxNodes` is capped at 31 (the same as
  the submission limit), and `submit` enforces that limit. Removing any of the five checks fails a
  test. The new invariant, with fewer slots than handler nodes, fails on the unfixed contracts with
  four active nodes under a cap of three. Storage layouts are unchanged; on a deployment this would
  be a UUPS upgrade of both contracts. The two new errors change the ABIs, which are regenerated. Porting the rule surfaced it:
  on Solana every activation checks the cap, and a round cannot hold more than 32 values.

## 14. Step 4b results — submitting from Go, and indexing

Oracle nodes submit to the Solana program from Go, and rounds, submissions, and the node set are indexed
into the existing oracle tables and served under `chain=solana-localnet`. The end-to-end test runs it
for real: three nodes register, a round opens, each node submits through the production adapter, the
round settles, and the indexer records it.

**What was built.**

- **`svm.OracleNodeChain`** — `oraclenode.Chain` for Solana. `CurrentRound` answers from the program's
  accounts: the feed's current round, the frozen node-set version, the node's activation, and whether
  a submission account already exists. `Submit` reads the node's nonce, signs the attestation, and
  sends the Ed25519 verification with `submit`, after checking the program is configured for the
  client's chain.
- **Transaction building moved into `internal/chain/svm`**, with simulation before sending. The
  end-to-end harness now builds every transaction with it, so the production builder runs against a
  real validator in both Solana tests.
- **The decoder now produces go-ethereum's shapes**: camelCase names, `uint8` as `uint8`, 32-byte arrays
  as `[32]byte`, other byte arrays as `[]byte`. It also accepts strings in events and fixed integer
  arrays in accounts. The indexer's oracle handlers take Solana events unchanged.
- **`svm.FeedID`** is keccak256 of the name, the same id as on Arbitrum, pinned by a `cast keccak`
  vector.
- **Wiring**:
  - the indexer registers both programs and refuses a Solana config naming separate staking and

  - the node binary takes a Solana branch with a `solana-keygen` JSON key;
  - the API serves the oracle module on Solana chains.
- **`scripts/solana-validator.sh` loads every program** with a committed IDL.

**The attestation layout is pinned in both languages.** One hex vector is asserted by a Rust test
against the program's `submission_message` and by a Go test against `SubmissionMessage`. The end-to-end
test verifies every stored signature off chain over those bytes, which is what 4c's aggregator will do.

**What building it found:**

- **Nodes read at `confirmed`, not `finalized`.** A round opened seconds earlier looked absent to a
  finalized read. Finalization trails by more than ten seconds, which a round of a minute or two cannot
  spare, and a rolled-back read costs only a failed simulation. Indexing stays at `finalized` (§2.7).
- **The staking handler assumed every event from its contract was a staking event.** On Arbitrum
  staking and rounds are separate contracts, so that held. On Solana one program emits both, and the
  first `FeedRegistered` failed the batch. The handler now ignores names it does not own.
- **The indexer marked a node active whenever it cancelled an unstake.** A cancel does not always
  reactivate: not below the minimum stake, and, since ORC-2, not into a full set. The contract signals
  activity with `NodeReactivated` and `NodeDeactivated`, and those are now the only events that set it.
  This was wrong on Arbitrum too, for a cancel below the minimum.
- **A mutation script counted a build failure as a survivor.** Two of its mutants left variables
  unused and did not compile. With compile-safe mutants, each check in the node chain fails a test
  when removed. Separately, the chain-id test had been passing for the wrong reason, failing earlier
  on a missing node account; it now supplies one, so only the chain id can stop it.

**Not exercised.** The `oraclenode` binary was not run against the validator. The test drives the same
adapter in-process.

## 16. Step 5 design — the Arbitrum dispatcher (*proposed*)

Today a passed proposal whose action names another chain reaches `Timelock.execute` and reverts with
`CrossChainDispatchUnavailable`. Step 5 makes that branch publish a Wormhole message. The Solana side
that receives it is step 6, but the message format is fixed here, because both ends depend on it.

**16.1 A separate `WormholeDispatcher` contract; the Timelock calls it.** The Timelock stays the only
holder of a proposal's delay and the only caller the dispatcher accepts, through a `DISPATCHER_CALLER`
role granted to the Timelock alone. The dispatcher holds the Wormhole core address and a route table.
Keeping Wormhole out of the Timelock keeps the contract that performs local calls free of a bridge
dependency, and means a bridge change is a dispatcher upgrade, not a Timelock upgrade.

**16.2 Routes are explicit, and an unknown one refuses.** A route maps a destination `targetChainId`,
our registry id, to a Wormhole chain id and the receiver's 32-byte address there. It is set by
`DEFAULT_ADMIN_ROLE`, which is governance itself once roles migrate. Executing an action with no route
reverts and leaves the proposal queued, so it can be cancelled. Nothing guesses a destination.

**16.3 The message format, version 1.** Packed and big-endian, as Wormhole payloads conventionally are:

| Field | Bytes | Meaning |
|---|---|---|
| version | 1 | `1` |
| sourceChainId | 8 | the registry id of the chain that voted |
| operationId | 8 | the Timelock operation, for correlation (§2.10) |
| targetChainId | 8 | the registry id the action is for |
| target | 32 | the program the action calls |
| value | 32 | the action's declared value, for the receiver's caps |
| payload | rest | opaque to the dispatcher; its layout belongs to the receiver (step 6) |

`targetChainId` travels inside the message, so the receiver can refuse a message meant for another
cluster even if a route were misconfigured. The emitter, which the receiver allowlists (§2.9), is the
dispatcher contract, and Wormhole's per-emitter sequence identifies each message.

**16.4 A remote action moves no ETH.** For a local action, `value` is ETH sent with the call. For a
remote one it cannot be, so it is carried in the message as a declared value for the receiver's caps.
The Governor refuses at proposal time a remote action whose route does not exist, so a vote is never
spent on something that cannot dispatch. The route is checked again at execution, since routes can
change during the vote.

**16.5 Dispatched is not executed.** The Timelock operation gains a `DISPATCHED` state, appended to the
enum. A dispatched operation emits `OperationDispatched(operationId, targetChainId, sequence)`, and its
proposal moves to the existing `DISPATCHED` state with the existing `ProposalDispatched` event. Whether
the action then ran on Solana is observed there, not reported back (§2.10).

**16.6 Wormhole's message fee comes from the Timelock's balance.** The Timelock already holds the
treasury actions spend from. It forwards exactly `messageFee()`, and a balance that cannot cover it
reverts, as an unaffordable local call does today. The fee is zero on the local test deployment, and a
test with a non-zero fee proves the forwarding.

**16.7 Consistency level: finalized.** The message is published at Wormhole's finalized consistency
level, so guardians sign only after Arbitrum finality. A governance action is worth waiting for.

**16.8 The storage-layout check learns gap carving.** The Timelock needs one new storage slot for its
dispatcher. The standard way to add it is to shrink the trailing `__gap` by one, but the current check
treats any change as a divergence. The EVM check gains the same rule as the Solana one (§8.7): new
variables may be taken from the trailing gap, provided every existing variable keeps its slot and
offset and the gap's end does not move. Anything else still fails. The rule gets its own mutation
tests, since a looser check is the risk here.

**16.9 Tests.**
- **Unit, with a recording Wormhole mock:** message bytes; route refusal; ETH not moved; fee
  forwarding; the `DISPATCHER_CALLER` role; state and events.
- **End to end:** Wormhole's own core contracts are deployed to Anvil from a separate Foundry project,
  `tools/wormhole`, vendored at a pinned commit because they build against OpenZeppelin 4 (§6.4). A
  proposal targeting `solana-localnet` passes, queues, and executes. The test asserts the core emitted
  `LogMessagePublished` from the dispatcher with exactly the §16.3 bytes, that the proposal is
  `dispatched` in the API, and that the Solana program saw no call. Signing and delivering the VAA is
  step 6.

## 18. Step 6 design — the Solana governance receiver (*proposed*)

The receiver is the last link: it takes a dispatched message off Wormhole and, after a delay, performs
the action as governance's authority on Solana. §2.9 fixed its controls. This section decides how each
works, and flags one place where §2.9's wording promised more than a naive design delivers.

**18.1 The value caps cannot trust the message's declared value.** §16.3 carries a `value` the DAO
declares. A forged message — exactly the case the caps exist for — can declare zero. So capping
declared value would leave a forged drain uncapped, contradicting §2.9's "bounded by the value caps".

**Proposed: caps measure what actually leaves, and only allowlisted programs may be called.**

- **Treasury accounts are registered.** The receiver keeps a list of the authority's treasury: SPL
  token accounts, and the authority's own lamports.
- **Every execution measures outflow.** Execution snapshots those balances before the CPI and compares
  them after. The outflow is checked against a per-message cap and a rolling cap, per mint. The whole
  transaction reverts if either is exceeded.
- **Rolling means rolling.** The window is exact: the last 16 executions per mint are kept with their
  times, and anything inside the window counts. A bucket that refills would allow twice the cap across
  a window boundary.
- **The allowlist bounds non-transfer actions.** Only programs on the list can be called: at first the
  vault, the oracle, the token program, and the receiver itself. A role change moves no tokens, so for
  those actions the controls are the allowlist, the timelock, and the pause.

The declared value is still recorded, for display. **What remains:** tokens held by the authority
outside the registered treasury are not measured, so the runbook says to hold them only there.

**18.2 Receiving and executing are separate.**
- **`receive_message`** verifies the VAA through the shim (§6), and checks the emitter, which is the
  dispatcher on Wormhole chain 23. It parses the §16.3 message and refuses a version other than 1 or a
  `targetChainId` other than this cluster's. It then stores the message with
  `executable_at = received_at + delay`.
- **`execute`** can be called by anyone once the delay has passed and the receiver is not paused.
- **Replay protection** is the message account itself, at `["message", emitter_chain, sequence]`: a
  second receive of the same VAA fails because the account exists. An executed message cannot run again
  because its state has moved.

**18.3 The payload layout** (the part §16.3 left to the receiver): `accounts_hash (32) ‖ instruction
data`. `accounts_hash` is SHA-256 over each account's `pubkey ‖ is_signer ‖ is_writable`, in order.
`execute` hashes the accounts it is given and refuses a mismatch, so the executor cannot choose the
accounts the DAO voted on. The authority PDA's signer flag is part of the hash, so a message cannot
gain the authority's signature on an account list the DAO did not see.

**18.4 A pause authority and a canceller, as on Arbitrum.**
- **The guardian.** A hot key, like `GOVERNANCE_GUARDIAN_ROLE`. It can pause receiving and executing,
  and can cancel a pending message.
- **Why cancelling matters.** Cancelling is what makes the timelock a defence. A forged message waits
  in public, and someone must be able to stop it for good, not just delay it.
- **Unpausing, and every parameter, is governance's.** The delay, caps, treasury, allowlist, emitter,
  and guardian are changed only by the authority PDA, meaning by a message that itself waited out the
  delay. There is a floor on the delay of one hour.

**18.5 Messages execute independently, in any order.** Enforcing Wormhole sequence order would let one
unrelayed message block every later one forever. An action that depends on another is expressed as
one message.

**18.6 Setup, and the handover to governance.** Only the upgrade authority can initialize, as for the
vault and oracle. Roles move to the authority PDA through the existing two-step admin handover:
`propose_admin` by the current admin, then `accept_admin`, which only the authority can sign. Only a
governance message can produce that signature. The step-6 end-to-end test does exactly this, so the
first governance action executed on Solana is taking ownership of the vault.

**18.7 Relaying is manual in v2.0.** Anyone can relay a signed VAA; nothing depends on who does. The
end-to-end test plays guardian and relayer. An automatic relayer service goes in `DEFERRED.md`,
triggered by a deployment.

**18.8 Indexing, for §2.10's correlation.** The receiver emits `MessageReceived`, `MessageExecuted`,
and `MessageCancelled` with the source chain, operation id, and sequence. They are indexed into a new
`governance_remote_actions` table, and the governance API shows a dispatched proposal's remote status
by operation id. The UI is step 7.

**18.9 Wormhole's Solana programs are committed.** The core bridge and verify-VAA shim binaries go in
`solana/external/` with their SHA-256 hashes (§6), checked in CI, so no test depends on reaching
mainnet. The validator script loads them at their mainnet addresses and initializes the core bridge with

## 19. Step 6a results — the receiver program

A message dispatched from Arbitrum, signed by the test guardian and checked by Wormhole's own shim and
core bridge, is stored, waits out its delay, and is executed as the authority. The first action tested
is the vault's `accept_admin`, after which the vault's admin is the authority.

**What was built.**

- **`solana/external/`** — the mainnet core bridge and verify-VAA shim, pinned by SHA-256 and checked in
  CI by `make solana-external-check`.
- **`solana/programs/aegis_governance_receiver`**, id `GJB8hFodVCW6cBWiiaYurMdKJk98Q4SkM3AbrC3GNZL5`:
  - **Receiving:** `receive_message` checks the emitter, version and cluster, then verifies the VAA
    digest through the shim. The message account at `["message", emitter_chain, sequence]` refuses a
    replay.
  - **Executing:** `execute` requires the delay to have passed, a pending message, an allowlisted
    target, and the voted account hash. It also requires every registered treasury, in increasing mint
    order. The message is marked executed before the call. The call is refused unless `execute` is a
    transaction-level instruction, so a message cannot run another inside itself.
  - **Measured outflow:** the SPL token accounts and the authority's lamports are read before and after
    the call. The outflow is checked against the per-message cap and the exact 16-entry rolling window,
    kept in a `Window` account apart from the caps. A treasury token account that ends with another
    owner or mint, or is closed, counts as fully spent. One that ends with a delegate or close authority
    is refused.
  - **Guardian and governance:** the guardian pauses and cancels. Unpausing, the delay (floor one hour),
    window, emitter, guardian, allowlist and treasuries belong to the authority. Until `finish_bootstrap`
    they also belong to the upgrade authority that initialized, so the first allowlist and treasuries
    can be set.
- **Baselines:** the IDL and account layouts are recorded, and the program is added to `SOLANA_PROGRAMS`.

**Tests.**

- **Unit tests (11):** the VAA and message parser, the account hash, the rolling window and its
  boundary, and token balance measurement.
- **LiteSVM tests (20):** these load both Wormhole binaries at their mainnet addresses. They initialize
  the core bridge with Wormhole's development guardian, and a test checks that key's address. Covered:
  - a VAA from another emitter address or chain;
  - a VAA signed outside the guardian set;
  - a payload altered after signing;
  - a replayed VAA;
  - the wrong version or cluster;
  - execution before the delay, or while paused;
  - a cancelled message;
  - a changed, extended or re-flagged account list;
  - a program not on the allowlist;
  - per-message and rolling caps exceeded by real token and lamport transfers, with the reopening
    exactly one window later;
  - handing a treasury account to another owner, and approving a delegate;
  - missing, reordered, duplicated or read-only treasury accounts;
  - a treasury that is not the authority's;
  - parameter changes by any key but the authority once bootstrap ends;
  - a nested `execute`;
  - initialization by anyone but the upgrade authority;
  - a message with the maximum 512 bytes of instruction data.
- **Transaction size:** every test transaction is checked against Solana's 1232-byte limit, which
  LiteSVM does not enforce.
- **Mutations:** 40 guards were mutated, and 39 fail a test. The survivor is equivalent:
  `finish_bootstrap` clears `bootstrap_admin`, so dropping the `bootstrapping` condition leaves only the
  all-zero key, which cannot sign.

**What building it found:**

- **A pause could never be lifted.** §18.4 had the pause stop receiving and executing, and made
  unpausing governance's alone. Once bootstrap ends, the unpause message could then never be received
  or run. One message now passes a pause: `unpause` addressed to the receiver itself. It still waits out
  the delay and can still be cancelled. A test shows the same bytes addressed to another program are
  refused.
- **A key listed twice has one set of privileges.** A transaction merges an account's signer and
  writable flags across every place it appears. So the voted account list gives a repeated key the union
  of its flags at each position, and the authority is always a signer. The Go proposal builder in 6c
  must hash lists the same way.
- **The allowlist refused the System Program,** whose address is all zeros, through a zero-address
  check. The check was removed: an allowlist entry is its own PDA and needs none.
- **One mutation survived for a real gap.** Removing the check that a treasury's window is writable
  changed only the error: the runtime refused the write. A test now presents a read-only window and
  expects `TreasuryMismatch`.
- **One test was order-dependent.** Treasuries are sorted by random mint addresses, so which triple came
  first varied between runs. The test now places the accounts explicitly.

**Deferred** (`DEFERRED.md`, v2.0):
- manual relaying;
- tokens held outside a registered treasury;
- messages that are never closed;
- the mainnet-only Wormhole addresses.

## 20. Steps 6b and 6c results — indexing the receiver, and governance across chains

A proposal voted on Arbitrum now takes effect on Solana, and both chains' indexers and the API show
it. The end-to-end test's action is the one §18.6 named: the Solana vault's admin role passes to the
receiver's authority.

**What was built.**

- **Configuration:** `CONTRACT_GOVERNANCE_RECEIVER` names the receiver program on a Solana cluster.
  Setting it on an EVM chain fails startup.
- **Database:** migration `000011` adds `governance_remote_actions`, keyed where the action runs
  (chain, Wormhole emitter chain, sequence). Each row carries its source chain and Timelock operation.
  It is `pending` until closed as `executed` or `cancelled`. A close applies only to a pending row, so a
  replayed batch cannot turn an executed action into a cancelled one. No foreign key reaches the
  proposal, because each chain has its own indexer and neither waits for the other.
- **Indexing:** `GovernanceReceiverHandler` indexes `MessageReceived`, `MessageExecuted` and
  `MessageCancelled` from the receiver's embedded IDL.
- **API:**
  - A proposal read from Arbitrum carries `remote`: the action received for its operation on its
    target chain, if one has been indexed.
  - Solana serves `GET /v1/governance/remote-actions`, filterable by status. The route answers 404 on a
    chain that receives nothing.
  - A dispatched proposal's own state stays `dispatched`. What happened on the destination is the
    destination's record, joined in when read.
- **Local validator:** `scripts/solana-validator.sh` loads Wormhole's two binaries at their mainnet
  addresses. The Go test initializes the core bridge with the test guardian.
- **Guardian signing:** `evm.SignVAABody` signs a VAA body as a guardian does. It lives behind the EVM
  boundary with go-ethereum's other uses, which the architecture test enforces.

**The end-to-end test** `TestAnArbitrumProposalTakesTheSolanaVaultAdminRoleThroughWormhole`:

- **Setup:** deploys Wormhole's core and governance on Anvil, routed to `solana-localnet`. On the
  validator it initializes the receiver, points it at that dispatcher, and has the vault propose the
  receiver's authority as admin.
- **Proposal:** proposes, votes, queues and executes the vault's `accept_admin`. The voted account hash
  is computed in Go.
- **Relay:** signs the published body as the guardian, posts the signatures to Wormhole's shim, and
  delivers the message.
- **Refused on the way:**
  - a VAA signed by a non-guardian;
  - a guardian-signed VAA from another emitter, with `UnknownEmitter`;
  - an execution before the delay, with `DelayNotElapsed`.
- **After the delay:** it executes, and reads the vault's admin at the offset in the committed layout
  baseline: it is the authority. A second execution is refused.
- **Indexing and API:** it indexes both chains into one database. There is exactly one remote action,
  `executed`, with the right operation, source chain, sequence, target and transactions. The Arbitrum
  proposal's `remote.status` is `executed`, and Solana's remote-actions list serves it.

**Mutations, each run against the whole stack** (4 of 4 caught):

| Mutation | Caught by |
|---|---|
| The receiver's emitter check removed | the forged-emitter delivery is received |
| `MessageExecuted` indexed as cancelled | the indexed status |
| Remote actions not attached to proposals | the Arbitrum proposal's `remote` is missing |
| The vault voted read-only | execution fails its account hash: the Go hash and the program's agree, byte for byte |

**Unit tests:**
- the handler: fields, both closes, foreign events, malformed events;
- the API: string serialisation of sequence and operation, status validation, 404 without a receiver,
  and `remote` on a proposal;
- the config;
- the guardian signature: it recovers the development guardian from the double-keccak digest, and not
  from a single hash.

**What building it found:**

- **The one-hour delay floor cannot be waited out by an end-to-end test.** The local validator's clock
  follows wall time. The receiver gains a `localnet` feature that lowers only `MIN_DELAY`, to 5
  seconds. `make solana-build` builds it into `solana/target/localnet/`, and the validator script
  prefers that build. The LiteSVM tests, the IDL and the layouts all use the default build, whose floor
  is an hour and is tested.
- **Guardian signing crossed the EVM boundary.** The first version of the test imported go-ethereum
  directly, and the architecture test refused it.
- **A payer funded too late made a transaction vanish rather than fail.** Sent without preflight from
  an account holding nothing, it is dropped before execution, so it never confirms. The test now funds
  the upgrade authority first.
- **The EVM store's comment promised a state change that would couple two indexers.** It said the
  indexer resolves `dispatched` on confirmation from the destination. It now says the destination's
  record is joined in when the proposal is read.
- **The local validator was pruning the history an earlier test indexes.**
  - `solana-test-validator` keeps 10,000 shreds by default.
  - With this step's larger transactions in the suite, the slots the Solana deposit test indexes from
    were gone by the time it ran.
  - The indexer refused the pruned range, as §10 designed it to, and the test failed.
  - The validator script now keeps 2,000,000 shreds.
