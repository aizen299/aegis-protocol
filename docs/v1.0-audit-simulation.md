# v1.0 internal audit simulation

Build-order step 6. Scope and form are set by `docs/v1.0-production-plan.md` §2.7: an adversarial
review per module against the vulnerability tables already in `docs/solidity.md`, `docs/oracle.md`,
and `docs/zk.md`, producing findings as a statement of the defect, a concrete failure scenario, and
either a fix or an accepted-risk entry with a trigger.

This is not an external audit and the release notes must not describe it as one. It is the authors
reviewing their own work, which finds the defects the authors are capable of seeing.

**Date:** 2026-09-15. **Revision reviewed:** `main` at the v1.0 hardening branch point.

---

## 1. What was examined

| Module | Reviewed | Not reviewed |
|---|---|---|
| Vault (v0.1) | `VaultEngine` value paths: deposit, withdraw, strategy attach/detach, share conversion | Strategy implementations — none exist beyond the test double |
| Oracle (v0.2) | `OracleRounds` round lifecycle, submission, quorum, median; `OracleStaking` stake, unbond, slash; the Go aggregator's decision path | Node operator deployment, source-level data quality |
| Governance (v0.3) | `Governor` proposal/vote/queue, `Timelock` execution and role holding | Multisig operating procedure |
| zk (v0.4) | Circuit public inputs and binding, `ZkVaultGate` replay and domain, `CommitmentTree` insertion and root window | Barretenberg and the generated verifier as cryptographic artifacts — trusted, not audited here |
| Backend | Secret policy, indexer cursor/idempotency, slashing executor | Full API authorization surface |

Two findings were confirmed by writing a test that passes against the defect rather than by
argument. Both tests are committed — one inverted into a regression test after the fix, one left
passing as the record of an accepted risk.

**Seven findings. One fixed, six recorded.** No module produced zero findings.

## 2. Findings

### ZK-1 — A proof is a bearer instrument — High — *accepted for v1.0, with a hard trigger*

**Defect.** Nothing binds a proof to the account that submits it. The circuit's public inputs are
`(root, nullifier_hash, action_id, chain_id, gate)`; `msg.sender` appears in neither the circuit nor
`ZkVaultGate.executePrivateAction`. Any party who observes a valid proof can submit it.

**Failure scenario.** A user broadcasts `executePrivateAction`. An observer reads it from the
mempool, copies the calldata verbatim, and submits it with a higher priority fee. The observer's
transaction lands first, the nullifier is marked spent, and the user's transaction reverts with
`NullifierAlreadySpent`. The nullifier is permanent and derived deterministically from the secret,
so the user can never perform that action for that commitment again. Their deposit is not stolen,
but their capability is destroyed, irreversibly, by anyone willing to pay more gas.

Demonstrated by `test_aStrangerCanSubmitSomeoneElsesProof` in `contracts/test/unit/ZkVaultGate.t.sol`,
which is left passing deliberately: it is the record of this risk, and it will fail the moment a
submitter binding is introduced.

**Why it is accepted rather than fixed.** The gate currently confers no benefit — it marks a
nullifier spent and emits an event, and no contract acts on that event. The exposure today is
destruction of capability, not theft. The fix is a circuit change (a sixth public input for the
permitted submitter, which is also what makes relaying possible and is how Tornado-style systems
handle it), a regenerated verifier, and a regenerated proof fixture. That is v0.4 work reopened, and
doing it under a v1.0 hardening banner would ship a freshly changed circuit with less testing than
the one it replaced.

**Trigger — and this one is not a date.** Before any contract consumes `PrivateActionExecuted`, or
any function is gated on `isSpent`. At that moment the exposure changes from griefing to theft: the
frontrunner receives whatever the gate confers. No contract may act on this gate until the binding
exists.

### ORC-1 — Missed-round slashing is unimplemented, and the constants suggest otherwise — Medium — *recorded, decision needed*

**Defect.** `docs/oracle.md` specifies four slashable conditions. Two are implemented:
`OUTLIER_SUBMISSION` and `INVALID_SIGNATURE`. `MISSED_ROUND` has a declared reason code
(`ReasonMissedRound`) and a declared penalty (`penaltyMissedRoundBps = 50`) in
`backend/internal/oracle/aggregator.go`, and neither is referenced by any code path.
`CONSECUTIVE_MISSES` is not present at all. The aggregator iterates the submissions a round
received; it never iterates the eligible nodes that did not submit, so a non-submitting node is
invisible to it.

Unused Go constants do not fail a build, so the gap reads as implemented on inspection.

**Failure scenario.** Quorum is judged against `eligibleCount`, frozen at `openRound` from
`activeNodeCount`. An adversary registers nodes up to the minimum stake and never submits. The
denominator rises; the numerator does not. With `quorumBps` at 60%, an adversary holding just over
40% of active slots makes every round fail to reach quorum, and the feed stops settling. They are
never slashed, because the only penalty for not submitting is unimplemented. After the unbonding
period they withdraw their stake in full. The attack costs the time-value of locked capital and
nothing else — which is precisely the cost the missed-round penalty exists to raise.

**Options.** Implement missed-round slashing (the aggregator would need the eligible set per round,
which the `oracle_nodes` table and `nodeSetVersion` can supply), or delete the dead constants and
record the absent liveness penalty as accepted risk. Doing neither leaves the codebase claiming a
control it does not have, which is the worst of the three.

### GOV-1 — The proposal threshold was met with borrowed weight — Medium — **FIXED**

**Defect.** `Governor.propose` read `_token.getVotes(msg.sender)` — voting power as it stands
during the call. `AegisToken`'s clock is timestamps and `ERC20Votes` checkpoints a delegation
immediately, so power acquired inside the calling transaction counted toward the threshold.

**Failure scenario.** An attacker flash-borrows tokens, delegates to itself, calls `propose`, and
returns the tokens — one transaction, ending with zero balance and zero voting power. The proposal
threshold is the protocol's spam control, and a spam control that can be rented for one block's
interest is not one. Governance is then a queue an attacker controls the contents of: every holder
must evaluate proposals that cost nothing to create.

The vote itself was never exposed — `castVote` reads `getPastVotes` at `voteStart`, and quorum reads
`getPastTotalSupply`. Only proposal creation was affected.

**Fix.** `propose` now reads `getPastVotes(msg.sender, block.timestamp - 1)`. A same-transaction
loan has no power one second ago. The cost is that a holder must wait one second after acquiring
power before proposing, which no real holder notices.

Demonstrated by a `FlashProposer` contract that acquires, proposes, and returns in one call. It
passed before the fix and now expects `BelowProposalThreshold(0, threshold)`. It is paired with
`test_aHolderWhoHeldPowerBeforeThisTransactionCanPropose`, so "nobody can propose" cannot satisfy
the suite. The invariant handler's precondition was corrected to match the contract's rule; it had
guarded on current power, which after the fix would have generated only reverting calls.

### VLT-1 — Neither deposit nor withdraw accepts a slippage bound — Medium — *recorded, decision needed*

**Defect.** `deposit(assets, receiver)` returns shares and `withdraw(shares, receiver)` returns
assets, and neither accepts a minimum. `docs/solidity.md`'s vulnerability table lists "Frontrunning
— use commit-reveal or slippage params where needed", and this is unmet.

**Failure scenario.** Share price moves with `totalAssets()`, which reads the strategy. A user
submits a withdrawal; before it is included, the strategy reports a loss. The withdrawal executes at
the new, worse rate and the user receives materially fewer assets than the rate they saw. They had
no way to express a floor, so there is no revert — only a worse fill. The virtual-shares offset
defeats the classic first-depositor inflation attack, which is a different problem; it does nothing
about ordinary price movement between submission and inclusion.

**Why not fixed here.** Adding a minimum changes the external signature, which the indexer ABI, the
frontend, and the committed layout baselines all track. Overloads would avoid the break but leave
the unguarded entry points as the default. Either way it is an interface decision, not a hardening
patch.

### ZK-2 — The root window is fixed at deployment and unbounded at it — Low — *accepted*

`CommitmentTree.initialize` validates `rootHistorySize_ != 0` and nothing else, and there is no
setter. The value is permanent for the life of the proxy. Too small and honest proofs fail whenever
a deposit lands between reading the tree and submitting; too large and `isKnownRoot` — a linear scan
on the path of every private action — costs a storage read per entry. At the deployed value of 30
this is about 63k gas worst case, which is not a problem. It is only unfixable.

**Trigger:** any upgrade to `CommitmentTree`, which is the only occasion on which a setter can be
added, or evidence of honest proofs failing on the root window.

### ORC-3 — `setMaxNodes` has no ceiling, and settlement sorts in O(n²) — Low — *accepted*

`_median` is an insertion sort, justified in a comment as "bounded by the node set size, which the
staking contract caps". The cap is real and enforced. But `setMaxNodes` accepts any non-zero value,
so `ORACLE_MANAGER_ROLE` can raise the bound until settlement no longer fits in a block, at which
point no round can settle and no value can be read. The role is a trusted one and the failure is
loud rather than silent.

**Trigger:** any increase of `maxNodes` beyond the low hundreds, or the first deployment where
`ORACLE_MANAGER_ROLE` is not the timelock.

### ORC-2 — The submission nonce is per node, not per feed — Low — *accepted*

`OracleRounds` keeps one nonce per node across all feeds and requires an exact match. A node serving
two feeds must have its transactions mined in the order it signed them; reordering — which a node
does not control — reverts the later one with `InvalidNonce` and forces a re-sign. This is a
liveness and operability cost, not a security one: replay protection is intact either way.

**Trigger:** a second feed in production, or the first observed `InvalidNonce` revert from an honest
node.

## 3. What this review did not do

- No fuzzing or symbolic execution beyond the suites that already exist.
- The generated Honk verifier was treated as correct. A review that cannot evaluate a proof system
  should not imply that it did.
- Economic parameters — `quorumBps`, penalty sizes, `minimumStake` — were checked for internal
  consistency, not for whether they are the right numbers. ORC-1 is a missing mechanism, not a
  mis-set parameter.
- No review of operational procedure: key custody, multisig signer set, incident response.
