# v0.3 DAO Governance — Implementation Plan

Working document, not a locked spec. `docs/project-spec.md` §5 and §7 remain the reference; this
records how v0.3 gets built and where it proposes to diverge.

**Status:** awaiting sign-off on §2. Six decisions: two extend a locked constraint, one deviates
from a locked doc, and one is a policy call about what governance is allowed to control.

---

## 1. Scope

**In:** a voting token with checkpointed balances, proposal creation, voting, a timelock, and an
executor that does not assume its target is local.

**Out, deliberately:**

- **No dispatcher, no encoding abstraction, no bridge interface.** `project-spec.md` §7 is explicit
  that building a messaging abstraction in Phase 1 buys nothing and constrains the Phase 2 design.
  The non-local execution branch exists and is unreachable.
- **No transfer of existing roles to governance.** Building the capability and exercising it are
  separate decisions — see §2.4.
- **No off-chain vote aggregation or delegation UI.** Indexing and endpoints only.

---

## 2. Decisions needed before code

### 2.1 A voting token — *not named in the spec*

Voting needs weight, and the spec names no source. Three candidates:

| Source | Problem |
|---|---|
| Oracle stake (`OracleStaking`) | conflates two roles: oracle operators would control the protocol that governs them, and stake bought to influence a vote also earns oracle rewards |
| A bespoke registry | reimplements checkpointing, which is the part that is easy to get subtly wrong |
| `ERC20Votes` | none, other than being a contract the spec does not name |

**Proposed:** `AegisToken`, an `ERC20Votes` from OpenZeppelin. Checkpointed balances are what make
a snapshot possible at all, and hand-rolling them is how governance systems acquire
off-by-one-block bugs.

Supply is fixed at deployment and minted to the admin multisig. No inflation, no rewards — a
distribution model is a product decision this protocol has not made, and inventing one in a
contract is worse than leaving it out.

### 2.2 An action's target is 32 bytes, not an address — *extends §7 constraint 1*

`project-spec.md` §7 requires that any identity crossing a layer boundary is wide enough for a
Solana pubkey. A proposal action's target is exactly such an identity: §7 says a cross-chain
destination is a "(chain, program, payload) triple", and a Solana program is 32 bytes.

Typing it as `address` would bake EVM into the one structure §7 says must not assume a local
target — while nominally satisfying the requirement by carrying a chain ID beside it.

**Proposed:**

```solidity
struct Action {
    uint256 targetChainId;  // equals block.chainid for every proposal reachable in Phase 1
    bytes32 target;         // an EVM address occupies the low 20 bytes
    uint256 value;
    bytes payload;
}
```

The local branch narrows `target` to an `address` and reverts if the high 12 bytes are set — the
same check `types.Identity.EVMAddress` performs in the backend. `governance_proposals.target` is
already `TEXT`, so the schema needs no change.

### 2.3 One action per proposal — *matches the locked schema*

`docs/database.md` gives `governance_proposals` a single `target` and `calldata`. Batched actions
would change that.

**Proposed:** one action. Every parameter change, role grant, and revocation is a single call, and
the upgrade-then-initialise case is already one call through UUPS `upgradeToAndCall`.

**Deferred, with a real trigger:** batching becomes necessary the first time two changes must land
atomically or not at all — the shape of that is a migration where an old contract is disabled and a
new one enabled. Revisit when such a change is actually proposed, not before.

### 2.4 Governance is built but granted nothing — *needs an explicit decision*

`ORACLE_MANAGER_ROLE`, `VAULT_MANAGER_ROLE`, `UPGRADER_ROLE`, and `DEFAULT_ADMIN_ROLE` are held by
a multisig today. Governance is only meaningful once it holds some of them.

**Proposed:** v0.3 builds the capability and transfers nothing. Granting an unaudited governance
system authority over live contracts inverts the safe ordering — the migration is a v1.0 step, after
the internal audit simulation the roadmap already calls for.

The recipient in that migration is the **`Timelock`**, not the `Governor`. The timelock is the
`msg.sender` of every executed action, so pointing roles at it means a governor can later be
replaced by re-granting three roles on one contract instead of migrating every protocol role again
— and a bug in vote counting does not immediately mean loss of the protocol, because the delay and
the canceller still stand between a vote and a call.

What v0.3 does deliver is the procedure, written down and tested against local deployments:

1. The timelock receives the role while the multisig retains it.
2. A proposal exercises it end to end on a local chain.
3. The multisig renounces, one role at a time, most reversible first.

`SLASHER_ROLE` is deliberately last and may never move: it is a hot key whose value is being
rotatable quickly, and routing rotation through a multi-day timelock is strictly worse for the
threat it exists to answer.

### 2.5 Parameters

| Parameter | Value | Why |
|---|---|---|
| `votingDelay` | 1 day | holders need time to see a proposal before the snapshot |
| `votingPeriod` | 7 days | long enough that a weekend does not decide a vote |
| `proposalThreshold` | 1% of supply | spam costs something without excluding real holders |
| `quorum` | 4% of supply | a vote nobody attends should not pass |
| `timelockDelay` | 2 days | a passed proposal is observable before it takes effect |

### 2.7 The vote clock is timestamps, not block numbers — *applies v0.2 §2.1*

`ERC20Votes` checkpoints against a clock that defaults to block numbers. Governance periods measured
in blocks have the same problem oracle rounds did: Arbitrum produces blocks roughly every 0.25s and
irregularly, so "7 days" becomes a number that drifts, and blocks are not a comparable unit on
Solana at all.

`clock()` returns `block.timestamp` and `CLOCK_MODE()` reports `mode=timestamp`, so a voting period
is seven days because it says seven days. Not raised as a separate decision: it is the already
approved v0.2 §2.1 reasoning applied to a second contract.

### 2.6 Snapshot at `creation + votingDelay`, not at the creation block — *deviates from `docs/solidity.md`*

`docs/solidity.md` lists the flash-loan mitigation as "snapshot voting power at proposal creation
block". Snapshotting at `creation + votingDelay` instead is proposed.

Both defeat a flash loan, and for the same reason: weight is read from a fixed past block, and a
loan cannot be held across a block boundary. The delay adds something the creation block does not —
a window in which holders who disagree can delegate or acquire before weights are fixed. Without
it, a proposer chooses the exact moment the electorate is measured, which is a smaller version of
the same problem.

This is also what OpenZeppelin's `Governor` does, so taking the documented wording literally would
mean hand-rolling a snapshot rule that differs from the audited one for no gain.

**Proposed:** snapshot at `creation + votingDelay`, and amend `docs/solidity.md` to say so rather
than leave the two disagreeing.

## 3. On-chain design

Three contracts, for the same size and blast-radius reasons the oracle was split:

| Contract | Holds | Upgradeable |
|---|---|---|
| `AegisToken` | balances and vote checkpoints | no — a token whose code can change is a token whose supply can |
| `Governor` | proposals, votes, state machine | UUPS |
| `Timelock` | queued actions and the delay | UUPS |

`AegisToken` is deliberately not upgradeable. Everything else in this protocol is, because the
logic may need to change; a token's entire value is that its rules cannot.

### State machine

```
pending ──> active ──> succeeded ──> queued ──> executed        (local; the only Phase 1 path)
   │                       │                └──> dispatched ──> executed   (remote)
   │                       │                                └──> failed
   │                       └──> defeated
   └──> cancelled
```

`dispatched` is not terminal and is unreachable in Phase 1. It exists so that adding it later is not
a migration of the state machine — the argument is in `project-spec.md` §7, and
`governance_proposals` already carries these states.

### Events

```solidity
event ProposalCreated(
    uint256 indexed proposalId, address indexed proposer, uint256 targetChainId,
    bytes32 target, uint256 value, bytes payload, uint256 voteStart, uint256 voteEnd,
    string title, string description
);
event VoteCast(uint256 indexed proposalId, address indexed voter, uint8 support, uint256 weight, string reason);
event ProposalQueued(uint256 indexed proposalId, uint256 executableAt);
event ProposalExecuted(uint256 indexed proposalId);
event ProposalDispatched(uint256 indexed proposalId, uint256 indexed targetChainId);
event ProposalCancelled(uint256 indexed proposalId);
```

`ProposalCreated` carries the full action because the indexer must reconstruct what a proposal does
without a contract read — the same rule that made the oracle emit its nonce.

## 4. Risk register

| Risk | Severity | Mitigation | Residual |
|---|---|---|---|
| Flash-loan voting | High | snapshot at `creation + votingDelay`; a loan cannot cross a block | none |
| Proposal spam | Medium | `proposalThreshold` | a large holder can still spam; cancellation is the answer |
| A passed proposal is malicious | High | timelock makes it observable before it takes effect | only useful if someone is watching — the indexer surfaces queued proposals |
| Governance seizes roles prematurely | High | §2.4: nothing is granted in v0.3 | none while that holds |
| Quorum unreachable as supply concentrates | Medium | quorum is a fraction of supply, adjustable by governance | a governance system that cannot reach quorum cannot fix its own quorum |
| Executor assumes a local target | High | §2.2 and the branching executor | none |
| Vote weight double-counted via delegation | Medium | `ERC20Votes` accounting, not hand-rolled | inherited from OpenZeppelin |

**Unresolved:** the quorum deadlock is real and has no in-protocol answer. If supply concentrates
far enough that quorum becomes unreachable, governance cannot lower its own quorum. Worth stating
rather than pretending the parameter is safe in every distribution.

## 5. Build order

Each step ends green and independently reviewable. The end-to-end test comes before the backend,
which is the ordering v0.2 arrived at the hard way.

1. `AegisToken` with checkpointed votes and delegation.
2. `Governor`: proposal creation, the state machine, voting with snapshotted weight.
3. `Timelock` and the executor that branches on destination chain. — *done. The delay lives here,
   not in the governor: one clock, stamped at schedule time so a parameter change never moves a
   queue someone is already watching. The governor holds the timelock's proposer, executor, and
   canceller roles and is its only client, so the proposal state machine and the queue cannot
   disagree.*
4. Fuzz and invariants; Slither; record the `v0.3.0` layout baselines.
5. End-to-end: a proposal created, voted, queued, and executed against a real chain.
6. Migration `000007`, indexer handlers, read endpoints.
7. Extend the end-to-end suite through the indexer and API.
8. Write the role-migration procedure from §2.4 and test it on a local deployment.

---

## 6. Invariants worth stating up front

- A proposal's vote totals never exceed the token's total supply at its snapshot block.
- No account's counted weight exceeds its balance at the snapshot block.
- One vote per account per proposal.
- A proposal cannot be executed before its timelock elapses.
- A proposal cannot be executed twice.
- A cancelled proposal can never reach `executed`.
- Only a `succeeded` proposal can be queued, and only a `queued` one executed.
- A proposal whose `targetChainId` is not the local chain never performs a local call.
