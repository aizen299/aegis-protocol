# v1.0 Production Release — Implementation Plan

Working document, not a locked spec. `docs/project-spec.md` and `docs/devops.md` remain the
reference; this records how v1.0 gets built and where it proposes to diverge.

**Status:** awaiting sign-off on §2. Seven decisions. Two correct thresholds that are wrong for
this chain, one is a scope boundary worth stating in writing, and one decides how far the role
migration actually goes.

---

## 1. Scope

`project-spec.md` §5 gives v1.0 as: security hardening, load testing, monitoring integration, AWS
staging deployment, internal audit simulation.

**In:** the seven required CloudWatch alarms and the metrics they need, a load profile with stated
pass criteria, the staging deployment applied for real, the secret path exercised against real SSM,
the role migration performed on staging, and a written adversarial review per module.

**Out, deliberately:**

- **No mainnet and no real funds.** `project-spec.md` §7 is explicit: Arbitrum Sepolia for staging,
  and Phase 1 ends there. §2.1 says what that means for the word "production".
- **No external audit.** The spec says audit *simulation*. An internal review is not a substitute
  and must not be described as one.
- **No Phase 2 work.** The multi-chain constraints are already binding; acting on them is Phase 2.
- **No frontend expansion.** The dashboard exists from v0.1. v1.0 hardens what serves it, not it.

---

## 2. Decisions needed before code

### 2.1 "Production release" means production-*ready*, not in production

Every other version name in this roadmap describes a thing that gets built. This one describes a
state of readiness, and the difference matters: a reader who sees `v1.0` tagged on a protocol that
has never held a real asset may reasonably conclude it is safe to hold one.

**Proposed:** v1.0 means the protocol is deployed to Arbitrum Sepolia, monitored, load-tested, and
reviewed — and that no line of it has been audited externally or has ever custodied value. The
README states this at the point it announces the release, not in a footnote.

This is a documentation decision, and it is first because the other six inherit from it.

### 2.2 The indexer lag alarm cannot be 100 blocks — *corrects `docs/devops.md`*

`docs/devops.md` requires an alarm at "indexer lag > 100 blocks". Arbitrum produces a block roughly
every 0.25 seconds, so 100 blocks is about **25 seconds** of lag — which a single batch of the
indexer's own 2000-block window passes through routinely.

This is the same error the oracle plan caught in v0.2 §2.1: a block count is an unstable unit of
time, and the number was written for a chain with twelve-second blocks.

**Proposed:** alarm on lag measured in **seconds**, derived from the head block's timestamp minus
the cursor block's timestamp, with the threshold set after observing the staging baseline rather
than guessed now. The block count is still emitted, because it is what an operator debugging a
stalled cursor actually wants to see.

**Consequence:** `DEFERRED.md`'s indexer-lag entry closes here, and it needs a metric before it can
need an alarm. The indexer logs lag today and emits nothing.

### 2.3 What the remaining alarms need before they can exist

**Corrected after looking properly:** three alarms already exist — `api_5xx`, `api_latency_p99` and
`indexer_stopped` — not one. An earlier count here said one because the pattern used to find them
did not match a name containing a digit. Five of the seven required alarms were missing, and
`indexer_stopped` is an extra rather than one of the seven: it catches a crashed indexer, not a
stalled one.

**Proposed:** all seven defined in `infra/modules/ecs/alarms.tf` alongside the existing one, with
the two application metrics (lag, and API latency percentiles) emitted from the Go services. An
alarm whose metric is never published is worse than no alarm: it sits permanently in
`INSUFFICIENT_DATA` and reads as healthy at a glance.

**Proposed check:** a test that fails if an alarm references a metric no service emits. That is the
"empty is not a match" rule this project has already applied to storage layouts, ABIs, and the
generated Poseidon.

**One alarm is a proxy, stated as such.** ECS publishes no restart counter. A restarting task shows
up as the running count dipping below what the service wants, so that is what the alarm watches —
which is not the metric the requirement names, and pretending otherwise would be worse than the
gap.

**The API alarms read the load balancer, not the service.** `TargetResponseTime` and
`HTTPCode_Target_5XX_Count` are what a client experiences, including failures the service never saw.
The service's own latency and request counts are emitted for per-endpoint debugging, not for these
alarms — so the check is that every alarm has a metric, not that every metric has an alarm.

### 2.4 How far the role migration goes on staging — *needs an explicit decision*

`docs/role-migration.md` was written and tested at v0.3 and deliberately not performed. v1.0 is
where it runs. The runbook has four stages, and the fourth is irreversible.

**Proposed:** run stages 1–3 on staging for `VAULT_MANAGER_ROLE` and `ORACLE_MANAGER_ROLE`. Do
**not** perform stage 4. Moving `DEFAULT_ADMIN_ROLE` to the timelock has no recovery path, and
staging is the wrong place to prove an irreversible thing — its value is that mistakes there are
cheap, which stage 4 specifically is not.

`PAUSER_ROLE` stays with the multisig: a pause that takes two days to enact does not answer the
incident it exists for, as the runbook already records. `SLASHER_ROLE` never moves.

**What this leaves undone, stated plainly:** v1.0 will not have demonstrated stage 4. That is a
real gap in the readiness claim and belongs in the release notes rather than being quietly omitted.

### 2.5 Load testing has to test the indexer, not the chain

A load test that hammers the API measures Postgres and the read path. That is worth knowing, but
the component most likely to fall behind under real conditions is the indexer, and its load is set
by chain activity rather than by callers.

**Proposed:** two profiles.

| Profile | Drives | Pass criterion |
|---|---|---|
| Read path | API endpoints at increasing concurrency | p99 under the 2000ms alarm threshold, zero 5xx |
| Ingest path | A chain replaying a dense block range | lag returns to baseline; no batch retried more than once |

The ingest profile is the one with a real chance of failing, and it is the one nothing currently
exercises: the end-to-end suite indexes tens of events, not thousands.

### 2.6 The staging secret path has never been exercised

The `APP_ENV` policy is built and unit-tested: staging resolves exclusively from SSM, there is no
fallback, and tests prove staging cannot reach the development path. But no process has ever
fetched a real parameter from a real Parameter Store.

**Proposed:** the staging deployment is the test. A service that starts against real SSM and one
that fails closed when the parameter is absent are both required observations, and the second is
the one worth deliberately causing.

**Revised, 2026-09-15**, after the AWS deployment was deferred for want of an account. The
observations are taken against LocalStack instead: a real Parameter Store implementation, the
production SDK, the production `GetParameter`, real SecureString decryption. `make
secrets-localstack` runs it, and Backend CI runs it on every push.

What that does and does not settle:

| Observation | Status |
|---|---|
| A SecureString resolves to plaintext through the real provider | proven |
| An absent parameter fails startup, naming the reference, leaking nothing | proven |
| A whitespace parameter fails startup as empty | proven |
| Staging refuses the development source while a working SSM is reachable | proven — and this is the first time the alternative source was genuinely reachable |
| An ECS task role can reach SSM at all | **not proven; needs an account** |

*Building it found a defect the deployment would not have.* The SSM client resolves
`AWS_ENDPOINT_URL` and `AWS_ENDPOINT_URL_SSM` from the process environment at construction
(`ssm/endpoints.go`, `resolveBaseEndpoint`). A staging task with either variable set reads its
slasher key from that endpoint and still logs `provider=aws-ssm` — truthful about the source kind,
silent about the source location. That is the same failure the `APP_ENV` policy exists to prevent,
one layer down: not a fallback to a weaker source, but a redirect of the right one.

So the endpoint knob is a restriction rather than a test hook. `NewSSMProvider` refuses to start
when an ambient override is present, and only an explicitly passed `SSMOptions.Endpoint` is
honoured — which `BuildProviders` never passes, so no production path can be redirected at all. A
blank variable is not an override, because a deploy template that renders an empty value should not
fail startup.

### 2.7 What "internal audit simulation" produces

Left undefined, this becomes a re-read of the code that concludes it looks fine.

**Proposed:** an adversarial review per module against the vulnerability tables already in
`docs/solidity.md`, `docs/oracle.md`, and `docs/zk.md`, producing findings in the form this project
already uses — a statement of the defect, a concrete failure scenario, and either a fix or an
accepted-risk entry with a trigger. A review that produces no findings is reported as such, with
what was examined, rather than treated as a pass.

## 3. Risk register

| Risk | Severity | Mitigation | Residual |
|---|---|---|---|
| `v1.0` read as "audited" or "safe for funds" | High | §2.1, stated at the point of release | a reader who skips the line |
| Alarm on a metric nobody emits | High | §2.3, plus a check that fails on the mismatch | none |
| Lag alarm too tight to be useful | Medium | §2.2, threshold from observed baseline | a baseline measured on a quiet testnet |
| Irreversible role change on staging | High | §2.4: stage 4 is not performed | stage 4 remains unproven |
| Indexer falls behind under real load | Medium | §2.5 ingest profile | testnet density is not mainnet density |
| Staging secrets fail closed only in theory | Medium | §2.6, against LocalStack rather than AWS | an ECS task role's reach into SSM is still unproven |
| A staging process reads its key from a redirected endpoint | High | §2.6: ambient `AWS_ENDPOINT_URL*` fails startup; only an explicit endpoint is honoured, and no production path passes one | shared-config `services.*.endpoint_url` is undetected, though a Fargate task has no shared config file |
| Review that finds nothing because it looked for nothing | Medium | §2.7 requires stating what was examined | reviewer blind spots |

**Unresolved:** load on Arbitrum Sepolia is not load on Arbitrum One. Every number this release
produces is a lower bound, and reporting them without that qualifier would overstate what was
measured.

## 4. Build order

Each step ends green and independently reviewable.

1. Metrics first: indexer lag in seconds and blocks, API latency percentiles. Alarms cannot precede
   the things they alarm on. — *done. Emitted through CloudWatch's Embedded Metric Format, which
   rides the `awslogs` driver already configured in `infra/modules/ecs`: no SDK, no credentials in
   the task, and no PutMetricData call on a request path. A metrics client that needs its own
   network call is one more thing that can fail while the service is trying to report a failure.*

   *Lag in seconds required a block timestamp, so `BlockTime` joins `chain.Client`. It is
   chain-generic — every chain stamps its blocks, and an SVM implementation would answer from a
   slot — so it does not widen the multi-chain boundary. Lag is measured against the wall clock
   rather than the head block's timestamp: a chain that stopped producing blocks entirely would
   otherwise report a lag of zero. When the block time is unavailable the block count is still
   emitted and indexing continues, because an indexer that stops because it could not report its
   lag has turned observability into an outage.*

   *Health and readiness are deliberately unmetered: the load balancer polls them far more often
   than any real endpoint, and including them would dilute both the latency percentile and the
   error rate until neither described user traffic. The error rate itself is not computed in the
   service — a percentage emitted per request is meaningless, and the alarm divides two sums over
   its own window.*

   *`EmittedMetricNames()` is the list step 2's alarm check reads, so an alarm on a metric outside
   it fails the build rather than sitting in INSUFFICIENT_DATA.*
2. The seven alarms in Terraform, plus the check that an alarm's metric exists. — *done. Five
   added: ECS tasks below desired, RDS CPU, RDS connections, Redis evictions, and indexer lag in
   seconds. RDS and Redis alarms live in their own modules rather than in `ecs`, so an alarm cannot
   outlive the thing it watches.*

   *Two Go tests enforce the link Terraform cannot: an alarm in the project's namespace must name a
   metric in `EmittedMetricNames()`, and must pin a `Service` dimension that a real service sets.
   Mutation-tested both ways — renaming the metric and misspelling the service each fail the build.*

   *Building this found a deployment bug. `APP_ENV` is required with no default, and nothing in
   `infra/` set it: both ECS tasks would have crash-looped on their first start. Compose set it;
   Terraform never did. It is now passed as a plain environment value on both task definitions,
   never from SSM — `APP_ENV` is what selects the secret source, so reading it from the secret store
   would be circular. It is also the `Environment` dimension every alarm matches on, so one variable
   feeds both and they cannot drift.*

   *`max_connections` is an explicit variable rather than a literal: RDS derives it from the
   instance class through the default parameter group, and an alarm computed against the wrong class
   is one that never fires — indistinguishable from a healthy database.*
3. Load profiles and their harness; record the baselines §2.2 needs. — *done, with one baseline
   still owed.*

   *The harness is open-loop. A closed-loop generator sends the next request after the previous one
   returns, so when the service slows the generator slows with it: offered load drops exactly when
   the system is under stress, and the percentiles describe a gentler test than the one intended.
   That is coordinated omission, and it is why load tests routinely report healthy numbers for
   systems that are visibly struggling. The cost is that a saturated run builds a backlog rather
   than applying backpressure, so a run reports how far behind its own schedule it fell — a run
   that slipped did not offer the rate it claims to have tested, and says so.*

   *The tool also fails a run where more than 5% of requests are rejected as client errors. Its
   first use sent a third of its requests at a path returning 404 and still reported a healthy p99:
   the percentiles described error handling, not the service.*

   **Baselines, measured locally on Anvil and Postgres in Docker:**

   | Profile | Offered | Result |
   |---|---|---|
   | Read | 200 req/s for 20s over two endpoints | p50 1.14ms, p95 1.85ms, **p99 2.51ms**, no errors, no schedule slip |
   | Ingest | 400 commitments across 400 blocks | indexed in **1.58s**, ~250 events/s, leaf indices contiguous |

   *Both are lower bounds and neither is a service level. The read p99 sits three orders of
   magnitude under the 2000ms alarm, which says more about a local Postgres than about staging. The
   ingest profile does not saturate the indexer either: producing 400 events through sequential
   transactions took 2m19s while indexing them took 1.58s, so the chain, not the indexer, was the
   bottleneck. What it does prove is that a dense range indexes completely, with contiguous and
   unduplicated leaf indices — a gap there is silent until someone tries to prove membership.*

   **Still owed:** §2.2's lag threshold needs a staging baseline, and staging is not deployed until
   step 4. The alarm stays provisional at 300s until then, which is stated at the resource.
4. Apply the staging environment for real; exercise the secret path including the failure case.
   — **blocked, and the scope needs a decision before it is unblocked.**

   *Applying needs AWS credentials this environment does not have, and it creates billable,
   outward-facing infrastructure — so it is the operator's to run regardless of credentials.*

   *Preparing for it surfaced a gap that would have wasted the apply: **no deployed service resolves
   a secret**. Only `aggregator` and `oraclenode` call `BuildProviders`, and the ECS module defines
   task definitions for `api` and `indexer` alone. §2.6 proposes to prove the staging secret path by
   deploying, and as the Terraform stands that deployment would exercise nothing — the SSM path
   would still never have run.*

   *This is a scope question rather than a bug, and it needs an explicit answer:*

   | Option | Consequence |
   |---|---|
   | Add ECS task definitions for `aggregator` and `oraclenode` | §2.6 is satisfiable; staging runs the services that hold keys, which is also what makes oracle slashing work at all in staging |
   | Deploy only `api` and `indexer` | v1.0 ships without the SSM path ever having run, and the role migration's slashing half is untestable on staging |

   *The first is the honest reading of "AWS staging deployment", since a staging environment missing
   the two services that hold keys is not the system. It is more work than this step assumed.*

   **Built in the meantime**, because it converts the failure this step would otherwise discover
   expensively into one the build refuses: a check that every ECS task definition provides the
   variables its service marks `required`. That is the generalisation of the `APP_ENV` bug found in
   step 2 — required with no default, set by docker-compose, never set by Terraform, and only
   visible because someone read the task definition. Mutation-tested by removing `APP_ENV` again,
   which fails with the reason. A second check pairs with it: a task definition for a service that
   resolves secrets must carry `AWS_REGION`, which `BuildProviders` requires outside local.
   **Re-scoped, 2026-09-15.** No AWS account exists for this project and none is planned, so the
   apply is deferred rather than performed — recorded in `DEFERRED.md` with the account's existence
   as its trigger. This is a deviation from `docs/project-spec.md` §5, which lists an AWS staging
   deployment for v1.0, and the release notes must say so plainly. What the apply would have proven
   is recovered where it can be — §2.6's secret path against LocalStack, done — and stated as
   unproven where it cannot: that the Terraform applies at all, and that a task role reaches SSM.
   The task-definition scope question above is deferred with it, unanswered.
5. Perform the role migration, stages 1–3, and record what was run. — *re-scoped to a local Anvil
   deployment, since staging will not exist. Stage 4 stays unperformed either way.*
6. Adversarial review per module; findings fixed or recorded. — *done. Seven findings, no module
   clean; written up in `docs/v1.0-audit-simulation.md` with what was examined and what was not.*

   *Two were confirmed by writing a test that passes against the defect rather than by argument. A
   stranger can submit someone else's zk proof — nothing binds a proof to a submitter — and the
   governance proposal threshold could be met with weight borrowed and returned inside one
   transaction.*

   *The governance one is fixed: `propose` now reads `getPastVotes` one tick back rather than
   `getVotes`, so a same-transaction loan has no power to spend. The attack test was inverted into a
   regression test and paired with a positive case, so "nobody can propose" cannot satisfy the
   suite. The invariant handler's precondition had to follow — it guarded on current power, which
   after the fix would have produced only reverting calls, quietly hollowing out the suite.*

   *The zk one is accepted with a trigger that is not a date: no contract may consume the gate until
   a submitter binding exists, because at that moment griefing becomes theft. The demonstrating test
   is left passing as the record.*

   *The review also found a control the codebase appears to have and does not: `MISSED_ROUND` has a
   declared reason code and a declared penalty, and no code path references either. Unused Go
   constants do not fail a build, so the gap reads as implemented. Quorum is judged against the
   eligible count, so nodes that stake and never submit raise the denominator for free and can halt
   a feed — which is the attack the missing penalty exists to price.*
7. Release notes stating precisely what v1.0 is and is not; tag `v1.0.0`.

## 5. Invariants worth stating up front

- Every alarm references a metric some service actually publishes.
- No service starts in staging or production with a secret that resolved from the environment.
- The indexer's cursor never advances past a block it has not fully processed.
- A load profile that fails reports which component saturated, not only that it failed.
- Nothing in the release notes claims an external audit, a mainnet deployment, or custody of value.
