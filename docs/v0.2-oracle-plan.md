# v0.2 Oracle Network — Implementation Plan

Working document, not a locked spec. `docs/oracle.md` remains the domain reference; this records
how v0.2 gets built and where it proposes to diverge.

**Status:** §2.1 and §2.4 approved. §2.2 and §2.3 were found while writing this plan and are
proceeding on a stated assumption — both are reversible, and the reasoning is recorded so the call
can be revisited rather than rediscovered.

---

## 1. Scope

**In:** node registration and staking, EIP-712 signed submissions, round lifecycle, on-chain
aggregation, slashing, the Go aggregation service, and a consumer interface for future modules.

**Out, deliberately:**

- **The vault does not consume prices in v0.2.** The consumer interface is defined so v0.3+ can
  read from it; wiring the vault to it is a later integration. Defining an interface early is
  allowed; implementing against it ahead of schedule is not.
- **Oracle prices never cross chains.** Each chain runs its own node set reporting to its own
  module (`project-spec.md` §7). No bridge surface here.
- Governance control of oracle parameters lands in v0.3. In v0.2 `ORACLE_MANAGER_ROLE` is a
  multisig.

## 2. Decisions needed before code

### 2.1 Round duration in seconds, not blocks — *deviates from `docs/oracle.md`* — **APPROVED**

`docs/oracle.md` says rounds close after `roundDuration` blocks. Arbitrum produces blocks roughly
every 0.25s and irregularly, so a block count is an unstable unit of time; and blocks are not a
comparable unit on Solana at all. This is the same class of assumption as the hardcoded 18
decimals — correct today, silently wrong at the first change of context.

**Proposed:** `roundDuration` is seconds, rounds close on `block.timestamp`. Miner timestamp
influence is seconds-scale and irrelevant against a 300s round.

### 2.2 The median is computed on-chain — *resolves a contradiction in `docs/oracle.md`* — **assumed, not yet confirmed**

`docs/oracle.md` says `OracleModule` "triggers aggregation after quorum" while the Go service
"computes the medianized result", yet `RoundSettled` carries `aggregatedValue` on-chain. Those
cannot all be true.

**Proposed:** the contract computes the median from stored submissions and settles with it. If the
backend computed the settled value, the on-chain price would be only as trustworthy as one hot key,
which discards the entire point of staking and slashing. The Go service still medianizes
independently — for analytics, outlier detection, and to detect a contract that disagrees with it.

Gas is bounded by capping `maxNodes` at 31. Insertion sort over ≤31 elements is cheap, and the node
set is protocol-controlled, so this is not an unbounded loop over user-supplied data.

### 2.3 An unbonding period on unstaking — *security gap in `docs/oracle.md`* — **assumed, not yet confirmed**

`docs/oracle.md` describes staking and slashing but no unbonding delay. Without one the slashing
design does not work: slashing is decided off-chain *after* a round settles, so a node can submit
bad data, watch the round settle, and unstake before the backend's slash transaction lands. Every
penalty in the table becomes optional for anyone paying attention.

**Proposed:** `requestUnstake()` starts a timer, `completeUnstake()` releases after
`unbondingPeriod` (7 days). Stake stays slashable throughout. Requesting unstake deactivates the
node immediately, so it cannot keep earning while winding down.

### 2.4 Slashing is capped on-chain — **APPROVED**

`SLASHER_ROLE` is a backend hot key by design. As specified it can zero every node's stake in one
transaction, which makes it the highest-value key in the protocol outside the admin multisig.

**Proposed:** the contract enforces a maximum of **10% of a node's stake per slash** and **one
slash per node per round**. The backend decides *whether* to slash; the contract decides what is
survivable. Every penalty in `docs/oracle.md`'s table (0.5%–10%) fits under the cap, so this
constrains a compromised key without constraining intended behaviour.

## 3. On-chain: `OracleModule.sol`

UUPS, `AccessControlUpgradeable`, `ReentrancyGuardUpgradeable`, `PausableUpgradeable` — same
pattern as `VaultEngine`, storage append-only with a committed layout baseline.

### Roles

| Role | Held by | Can |
|---|---|---|
| `DEFAULT_ADMIN_ROLE` | multisig | grant roles, deactivate nodes, set the unbonding period |
| `ORACLE_MANAGER_ROLE` | multisig | register feeds, set stake minimums, round duration, quorum |
| `SLASHER_ROLE` | backend hot key | `slash()`, within the caps in §2.4 |
| `PAUSER_ROLE` | ops | halt submissions |
| `UPGRADER_ROLE` | multisig | authorise upgrades |

### Round lifecycle

```
OPEN ──(quorum reached)──> QUORUM_MET ──(settle)──> SETTLED
  │
  └──(deadline passed, quorum not met)──> FAILED
```

`FAILED` is terminal and marks non-submitters as having missed the round. A feed's next round opens
on settlement or failure of the previous one, so a feed always has exactly one open round.

### Submissions

Nodes submit their own transactions — `msg.sender` must be the registered node, which keeps the gas
cost on the node and makes spam self-limiting (`docs/oracle.md`'s anti-griefing argument).

The EIP-712 signature is still required and still verified on-chain. It is not authentication —
`msg.sender` already provides that — it is a portable attestation the aggregation service can
verify independently of transaction provenance, and it is what a future relayed-submission design
would rest on.

```solidity
bytes32 constant SUBMISSION_TYPEHASH = keccak256(
    "Submission(uint256 roundId,bytes32 feedId,uint256 value,address node,uint256 nonce)"
);
```

Chain ID and verifying contract come from the EIP-712 domain separator, so a signature cannot be
replayed onto another chain or another deployment. `feedId` is in the payload so a signature for one
feed cannot be replayed onto another in the same round.

**Signatures are emitted, not stored.** 65 bytes per submission is three storage slots for data
only ever read off-chain; `docs/solidity.md` says to emit rather than store historical data. This
diverges from the `struct Submission` sketch in `docs/oracle.md`, which includes `bytes signature`.
The indexer takes it from the event.

### Events — the indexing surface

```solidity
event RoundStarted(uint256 indexed roundId, bytes32 indexed feedId, uint256 startedAt, uint256 deadline);
event SubmissionReceived(uint256 indexed roundId, address indexed node, uint256 value, bytes signature);
event RoundSettled(uint256 indexed roundId, bytes32 indexed feedId, uint256 aggregatedValue, uint256 submissionCount);
event RoundFailed(uint256 indexed roundId, bytes32 indexed feedId, uint256 submissionCount);

event NodeRegistered(address indexed node, uint256 stake);
event NodeStaked(address indexed node, uint256 amount, uint256 totalStake);
event UnstakeRequested(address indexed node, uint256 amount, uint256 claimableAt);
event NodeUnstaked(address indexed node, uint256 amount);
event NodeSlashed(address indexed node, uint256 amount, bytes32 indexed reason, uint256 roundId);
event NodeDeactivated(address indexed node, bytes32 reason);
```

`NodeSlashed` carries `roundId` so the audit trail links a penalty to the round that caused it.

### Consumer interface — fails closed on staleness

```solidity
interface IOracleReader {
    /// @param maxStaleness Seconds. Reverts if the newest settled round is older than this.
    function getValue(bytes32 feedId, uint256 maxStaleness)
        external view returns (uint256 value, uint256 settledAt, uint256 roundId);
}
```

There is deliberately **no `latestAnswer()`**. A getter that returns a price without forcing the
caller to state a freshness bound is how oracle consumers get exploited — the value looks fine and
is hours old. `maxStaleness` has no default; the caller states it or does not compile.

Values are scaled to 18 decimals by the contract. That scale is contractual, not a property of any
token, which is why oracle values stay `NUMERIC(38,18)` in Postgres while vault amounts are raw
base units (`docs/database.md`, "Token amounts").

### Proposed parameters

| Parameter | Value | Why |
|---|---|---|
| `roundDuration` | 300s | a price feed useful for risk decisions without being submission-spam |
| `quorumBps` | 6667 (2/3) | tolerates a third of nodes offline |
| `minQuorumNodes` | 3 | a 2/3 quorum of 2 nodes is not a quorum |
| `maxNodes` | 31 | bounds on-chain median gas |
| `minimumStake` | 10,000 tokens | registration floor |
| `minStakeFloor` | 5,000 tokens | auto-deactivate below this |
| `unbondingPeriod` | 7 days | must exceed round duration plus the slashing window with margin |
| `maxSlashBps` | 1000 (10%) | caps a compromised `SLASHER_ROLE` key |

All test-token denominated. No real funds in Phase 1.

## 4. Off-chain

### Oracle node (`backend/cmd/oraclenode`, one Docker container per node)

Fetches from N ≥ 3 sources, medianizes *source* values before signing, signs EIP-712, submits.
Exponential backoff, max 5 retries per round. A node that cannot reach quorum-worthy data skips the
round rather than submitting a guess — a missed round costs 0.5%, a bad submission costs 1% and
pollutes the median.

### Aggregation service (`backend/internal/oracle`)

Consumes `SubmissionReceived` and `RoundSettled` through the existing `chain.Client` interface —
no new EVM dependency outside `internal/chain/evm`. Verifies signatures off-chain, computes its own
median, flags outliers beyond `outlierThresholdPct` (5%), writes to Postgres and Redis, and
proposes slashes.

Two properties carried over from v0.1:

- Slashing decisions are written to Postgres **before** the on-chain transaction. The audit trail
  must survive the transaction failing.
- Slashing is never cached in Redis. It is an authoritative decision.

A disagreement between the contract's settled median and the service's own is an alert, not a
correction. The chain is authoritative.

## 5. Database — migration `000002`

Tables are already sketched in `docs/database.md`. Changes needed on top:

- `oracle_submissions` gains `log_index INT NOT NULL` and `UNIQUE (chain_id, tx_hash, log_index)`
  alongside the existing semantic key `(chain_id, round_id, node_address)`. Per the Event Identity
  rule, the semantic key expresses the protocol rule and the event key expresses idempotent
  ingestion; a table holding indexed events needs both.
- `oracle_rounds.feed_id` stays `TEXT` — the human name (`ETH/USD`), with the on-chain `bytes32`
  derivable from it.
- New `oracle_slashings` table: node, round, amount, reason, decided-at, executed-at, tx hash.
  Decision and execution are separate timestamps for the same reason `governance_proposals` splits
  `dispatched_at` from `executed_at` — an unexecuted decision is an operational alert.

## 6. Risk register

| Risk | Severity | Mitigation | Residual |
|---|---|---|---|
| Node unstakes before a slash lands | High | 7-day unbonding, §2.3 | none |
| `SLASHER_ROLE` key compromised | High | 10%/slash cap, one slash per node per round, §2.4 | attacker can still grind a node down over many rounds; rotation via governance in v0.3 |
| Colluding majority moves the median | High | median needs >50% collusion to shift materially; stake at risk | accepted — inherent to medianized oracles |
| Consumer reads a stale price | High | no `latestAnswer()`; `maxStaleness` is a required argument | none in-protocol; a consumer can still pass an absurd bound |
| Sybil node registration | Medium | stake minimum plus a manager-gated registry in v0.2 | permissionless registration deferred past v1.0 |
| Backend and contract medians disagree | Medium | chain is authoritative; divergence alerts | needs the metric to exist — see `DEFERRED.md` |
| Quorum never reached | Medium | round fails, non-submitters marked missed, feed keeps last settled value with staleness enforced by readers | a feed can go stale indefinitely if nodes stay offline |
| Data source outage correlated across nodes | Medium | N ≥ 3 sources per node, source-level median before signing | correlated outage across all nodes' sources still fails the round |
| Median gas grows with node count | Low | `maxNodes` = 31 | none |

**Unresolved:** nothing blocking. The residual on a compromised `SLASHER_ROLE` grinding a node down
over successive rounds is real but bounded and observable; a rolling cap would close it and is
deferred to v0.3 when governance can rotate the key.

## 7. Build order

Each step ends green and independently reviewable.

1. `OracleModule` staking and registration — stake, request unstake, complete unstake, deactivate.
   Tests first for the unstake-front-runs-slashing scenario, since that is what §2.3 exists for.
2. Round lifecycle and submissions, EIP-712 verification.
3. On-chain median and settlement, including the `FAILED` path.
4. Slashing with the caps from §2.4.
5. Slither, fuzz, invariants. Record the storage layout baseline as `v0.2.0`.
6. Migration `000002`, indexer handler for the oracle events.
7. Aggregation service: signature verification, medianization, outlier detection, slash proposals.
8. Oracle node binary and its Docker image.
9. Extend the E2E: a full round with three nodes, one of them an outlier, asserting the settled
   value on-chain matches the indexed value and that the outlier is slashed.

Step 9 is the one that proves it works. Steps 1–8 are each verifiable in isolation, and isolation
is what hid the v0.1 defects until the end-to-end test existed.

## 8. Invariants worth stating up front

- A node's recorded stake never exceeds the module's token balance.
- The sum of all slashes against a node never exceeds its stake at any point.
- A settled round's `aggregatedValue` is one of the submitted values, or the mean of the two
  middle ones — never a value no node submitted.
- No round settles with fewer than `quorumBps` of active nodes.
- A node that requested unstake cannot submit.
- Stake released by `completeUnstake` is never larger than what was requested.
