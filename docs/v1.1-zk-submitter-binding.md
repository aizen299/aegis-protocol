# Closing ZK-1: binding a proof to its submitter

The v1.0 internal review found that nothing tied a zk proof to the account presenting it. Anyone who
saw a proof — the mempool is the ordinary case — could copy the calldata, land it first, and
permanently burn the prover's nullifier. Their deposit was safe; their ability to act on it was not.

Accepted for v1.0 only because the gate conferred no benefit, with a trigger that was a precondition
rather than a date: no contract may consume the gate until this exists. Fixed here.

---

## The fix

The circuit takes a sixth public input, `submitter`, and the gate reads it from `msg.sender` rather
than from calldata:

```solidity
publicInputs[5] = bytes32(uint256(uint160(msg.sender)));
```

A stranger presenting a copied proof therefore presents a different public input, and the proof does
not verify. To have someone else submit — a relayer — prove against their address.

## Two things it would have been easy to get wrong

**The submitter must stay out of the nullifier.** Folding it into
`nullifier_of(secret, action, chain, gate)` would have made the nullifier vary with the submitting
address, so one commitment could be spent once per address. That trades a frontrunning bug for a
double-spend, which is worse. `the_nullifier_does_not_depend_on_the_submitter` holds the line.

**The binding needs no constraint, and the first attempt at one was theatre.** The circuit
originally carried `assert(s * s == s * s)` to force the input into the constraint system, on the
belief that an unreferenced public input could be optimised away.

Measured rather than assumed: the generated verifier was **byte-identical** with and without that
line — it is a tautology the compiler eliminates. And with it removed, tampering with the submitter
still invalidated the proof. UltraHonk folds every public input into the verification transcript,
referenced or not.

So the line was deleted rather than left implying a guarantee it never provided. What holds the
property now is a test, not a comment: `test_changingAnyPublicInputInvalidatesTheProof` tampers with
each public input in turn and requires every one to break the proof. If a future toolchain stopped
binding unreferenced inputs, that test fails at index 5.

## What proves it

| Check | Where |
|---|---|
| Every public input, submitter included, is bound to the proof | `contracts/test/unit/ZkVerifier.t.sol` |
| A stranger cannot present another account's proof, and the nullifier survives the attempt | `contracts/test/unit/ZkVaultGate.t.sol` |
| The named submitter still can | same test, second half |
| The nullifier is independent of the submitter | `zk/circuits/vault_membership/src/main.nr` |
| The service produces six public inputs, submitter last | `zk/tests/prove_integration.rs`, against real nargo and bb |
| A request with no submitter is refused rather than defaulted to zero | `zk/src/api/mod.rs` |
| End to end on a real chain: a stranger is refused, the prover succeeds | `backend/internal/e2e/zk_flow_test.go` |

## Regenerated artifacts

The verifier and the committed proof fixture are both functions of the circuit, so both were
regenerated from the pinned toolchain (`nargo 1.0.0-beta.22`, `bb 5.0.0-nightly.20260522`). Public
inputs went from 13 to 14 in the generated verifier — the circuit's six plus the pairing-point
object.

The gate's own bytecode changed, which moved its CREATE2 address in the test fixture, so the proof
had to be regenerated against the new address. The suite's `setUp` asserts that address and names
the regeneration command when it drifts, which is how it was caught rather than debugged.

Storage layout is unchanged: no state variable was added, removed, or reordered.
