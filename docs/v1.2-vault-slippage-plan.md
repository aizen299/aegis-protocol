# v1.2 — Slippage bounds on vault deposit and withdraw

Closes VLT-1, recorded in `DEFERRED.md` and found by the v1.0 internal review:
`docs/solidity.md`'s vulnerability table lists "Frontrunning — use commit-reveal or slippage params
where needed", and neither `deposit` nor `withdraw` accepts a bound.

Sequenced before the UI's write actions deliberately. The fix changes external signatures, so
building the write surface first would mean building it twice and churning the ABI twice.

---

## 1. The defect

Share price moves with `totalAssets()`, which reads the strategy. A user submits a withdrawal;
before it is included, the strategy reports a loss. The withdrawal executes at the new, worse rate
and the user receives materially fewer assets than the rate they saw. There is no revert — only a
worse fill — because they had no way to express a floor.

The virtual-shares offset defeats the first-depositor inflation attack. That is a different problem,
and it does nothing about price movement between submission and inclusion.

## 2. Decisions

### 2.1 Replace the signatures rather than overload them

`deposit(uint256,address)` becomes `deposit(uint256,address,uint256 minShares)`, and
`withdraw(uint256,address)` becomes `withdraw(uint256,address,uint256 minAssets)`.

An overload would be non-breaking, and that is exactly the objection: it leaves the unguarded entry
point as the path of least resistance, callable forever by anyone who does not know to avoid it. A
protection that the careless path skips is not a protection.

The break costs an ABI regeneration and a UI update. It costs no migration, because nothing is
deployed and no value is at stake — which is the cheapest this change will ever be.

### 2.2 The bounds

- `deposit` reverts when the shares minted are below `minShares`.
- `withdraw` reverts when the assets paid are below `minAssets`.

Checked after the amount is computed and before any state is written, so a rejected call leaves
nothing behind.

### 2.3 Zero means no bound, and that is stated rather than enforced away

`minShares == 0` and `minAssets == 0` are permitted and mean "no bound".

**The alternative considered and rejected:** require a non-zero bound, so the protection cannot be
opted out of. It was rejected because it is ceremony — a caller who wants no bound passes `1` and
satisfies it trivially, leaving a check that constrains nothing while implying it constrains
something. That is the same failure as ORC-1's dead constants and the zk circuit's tautological
`assert(s * s == s * s)`, both of which this project has already had to remove.

What the change actually buys is that the parameter *exists*: every caller now makes a decision, and
every interface that forgets to fails to compile. A caller passing zero has chosen to.

### 2.4 No deadline parameter

The classic pairing is a deadline, against a transaction sitting in the mempool and executing
against stale intent. Not added, because the bound already covers the harm: a stale transaction
either fills acceptably or reverts. A deadline would prevent a *late* fill that is nonetheless
within the bound the user set, which is not a loss.

**Revisit if** the vault gains an operation whose cost depends on when it lands rather than on the
price it lands at.

### 2.5 The events do not change

`Deposited` and `Withdrawn` carry what happened, not what was asked for. A bound is an input
constraint, not state, so the indexer's decoding surface is untouched and no migration is needed.

The committed ABI does change — function selectors move — so `make backend-abi` must run and the
drift check will name it if it does not.

## 3. Invariants

- A bound that is met changes nothing about the resulting position.
- A bound that is not met reverts, and no share, balance, or total is written.
- Storage layout is unchanged. No state variable is added, removed, or reordered.
- The existing vault UI passes a bound it computed, not a zero.

## 4. Build order

1. The contract change, with tests for both bounds met and unmet, and a test that a rejected call
   leaves no state behind.
2. Regenerate the committed ABI; confirm the drift check fails first and passes after.
3. Update the frontend's deposit and withdraw forms to compute and pass a bound, with the tolerance
   visible to the user rather than hidden.
4. Release notes; tag `v1.2.0`.
