# v1.1 — Frontend for the rest of the protocol

The backend serves and end-to-end tests four modules. The UI covers one. This closes that gap for
oracle and governance; the zk interface is deliberately last and blocked on a prerequisite.

Recorded in `DEFERRED.md` as "The UI covers the vault only". Not a spec violation —
`docs/project-spec.md` §3.5 fixes the frontend stack and never assigns per-version frontend
deliverables — but it is the largest gap between what the protocol does and what anyone can see it
do.

---

## 1. Scope

**In:** read-only oracle and governance surfaces, driven by the existing REST API.

**Out, deliberately:**

- **Write actions** — `castVote`, `queue`, `execute`. Deferred to 3a-plus, after the read surface is
  solid. Reading is where the protocol has zero visibility today, and it is the half that cannot
  cost anyone anything.
- **Oracle node registration, staking, unstaking.** Operator tooling, not a dashboard, and it moves
  real stake.
- **The zk interface.** Was blocked on ZK-1 — a UI is what first puts real proofs into a mempool, so
  shipping one against the old gate would not have inherited that risk, it would have activated it.
  ZK-1 is now fixed (see `docs/v1.1-zk-submitter-binding.md`), so 3b is unblocked. It stays after
  3a because the read surfaces exercise the API-fetch pattern first.

## 2. Decisions

### 2.1 Read-only

No wallet is required for anything in 3a. Every figure comes from the API.

This is not only a scope reduction. A read surface has no failure mode that costs a user anything,
so it can ship while the wallet questions in §2.2 are still being worked out.

### 2.2 Delegation is surfaced before an action, not after a revert

Recorded now because it governs 3a-plus, and because the trap is invisible until someone hits it.

`castVote` reads `getPastVotes` at the proposal's `voteStart`. A holder who has never delegated has
zero voting power, and self-delegating today does nothing for a proposal whose snapshot has already
passed. They see tokens in their wallet, click vote, and get a revert with no readable cause.

v1.0's GOV-1 fix adds a second one: `propose` reads power one tick back, so delegating and proposing
in the same transaction now fails by design. That is the same break that took out five end-to-end
tests when the fix landed — if it caught the test suite, it will catch users.

So when writes arrive, the UI shows delegated power beside balance, and disables voting with the
actual reason — "you had no delegated voting power when this proposal's snapshot was taken" — rather
than surfacing a revert.

### 2.3 The API is the source of truth; the chain answers only "can I act now"

The indexer processes to `head - confirmBlocks`, so a vote just cast does not appear in the API for
several blocks. A UI that silently mixes indexed and live reads contradicts itself, and the reader
cannot tell which number to believe.

History, tallies, and every listing come from the API. Chain reads are reserved for present-tense
capability — a viewer's delegated power, a proposal's live state — and anything read that way is
labelled live. The two are never merged into one figure.

### 2.4 `missedRounds` is shown, and labelled as unpenalised

`OracleNode.missedRounds` is populated and would ordinarily imply a consequence. There is none:
missed-round slashing is unimplemented (ORC-1 in `DEFERRED.md`). Rendering a bare count tells an
operator something untrue by implication.

It is displayed with an explicit note that it carries no penalty today. A dashboard that quietly
implies an enforcement that does not exist is worse than one that omits the number.

## 3. Invariants

- Every amount is rendered from its own scale — feed `decimals`, node stake `decimals`, vote
  `voteDecimals`. Nothing assumes 18. This is the rule the vault UI already follows and the reason
  `formatAmount` takes decimals rather than defaulting them.
- Loading, failed, and genuinely-absent stay distinguishable, for API fetches as they now are for
  contract reads. The defect that motivated step 2 is not to be reintroduced one layer up.
- A tally of zero renders as zero. An unreachable API renders as unavailable. They never look alike.
- No surface in 3a constructs a transaction.

## 4. Build order

1. The API client and its read-state handling, extending `readState` from the vault work to fetches.
2. Oracle: feed list, feed detail with round history, round detail with submissions and outliers.
3. Oracle: node table, including §2.4's labelling.
4. Governance: proposal list filtered by state.
5. Governance: proposal detail — action, tally, timelock countdown, vote list.
6. Navigation across all four surfaces, and the README updated to stop describing the UI as
   vault-only.

Oracle before governance: it is purely read-only and exercises the API-fetch pattern end to end,
where governance is where the wallet questions in §2.2 eventually land.

## 5. What building 3a found

Three defects, none of which were visible from reading the code.

**The API had no CORS headers, so no browser could call it.** Four releases of a REST API written
for a browser frontend, and no browser had ever reached it — because the frontend's API client was
dead code that nothing imported. Fixed with an allowlist that defaults to nobody: an unlisted origin
gets no header rather than a header naming someone else, and `"*"` is not treated as a match.

**A failing fetch rendered as "loading…" indefinitely.** react-query retries with exponential
backoff and stays pending throughout, so the CORS failure above showed as a spinner for as long as
anyone watched. That is the same collapse of failure into absence that step 2 fixed for contract
reads, reappearing one layer up inside the fix's own `Async` component. Retries are now bounded.

**The hand-written TypeScript had already drifted from the Go structs.** `Proposal` was missing
`dispatchedAt` and `logIndex`, and the older `fetchTvl` was typed `{ tvl: string }` against an
endpoint returning an object. Nothing connected the two languages, so both compiled. There is now a
drift check comparing the TypeScript types against the Go json tags, wired into Frontend CI and
triggered by changes to `backend/pkg/types` as well as to the frontend — mutation-tested three ways,
including that an unreadable struct fails rather than passes.

## 6. Not a release on its own

3a ends green and reviewable but is not tagged. `v1.1.0` is cut after 3b — the zk interface — so the
tag means every module has a UI, rather than three of four.
