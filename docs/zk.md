# zk Layer Domain Reference — Project Blockchain

## Scope (v0.4)

The zk layer adds privacy-enabled interactions to the protocol. Users can:
- Prove vault position membership without revealing balance.
- Execute governance votes without revealing identity (optional, post-v0.4).
- Interact with protocol actions that require proving knowledge without revealing inputs.

**Not in scope for v0.4**: full anonymous transaction graph (Tornado Cash-style). Scope is proof-of-membership and selective disclosure.

## Framework Decision: Circom vs Noir

This decision must be finalized pre-May. Current assessment:

| Criteria | Circom | Noir |
|---|---|---|
| Maturity | High (2019+, battle-tested) | Medium (2022+, growing fast) |
| Language feel | Low-level constraint system | High-level Rust-like |
| Proving backend | SnarkJS (PLONK/Groth16) | Barretenberg (UltraPlonk) |
| Rust integration | Via WASM/FFI | Native (Nargo CLI) |
| On-chain verifier | Solidity verifier generation | Solidity verifier generation |
| Learning curve | Steeper | Gentler |
| Production usage | High (Tornado, Semaphore, etc.) | Growing |

**Recommendation**: Circom if the team has prior constraint-system experience. Noir if starting fresh — the developer experience is significantly better and Barretenberg is production-viable.

## Architecture

```
[User Client (Next.js)]
    ↓ inputs (private)
[Rust Proof Service]
    - Receives inputs via API (TLS, no logging of private inputs)
    - Generates zk proof (Circom/Noir circuit)
    - Returns (proof, public_inputs)
        ↓
[Go Backend]
    - Orchestrates proof request
    - Submits (proof, public_inputs) to chain
        ↓
[ZkVerifier.sol]
    - Verifies proof on-chain
    - Emits VerificationResult
    - Gates protocol action on verification success
```

### Proof Generation (Circom example)

```rust
use ark_bn254::Bn254;
use ark_groth16::{Groth16, ProvingKey};
use ark_snark::SNARK;

pub async fn prove_vault_membership(
    params: VaultMembershipInputs,
    proving_key: &ProvingKey<Bn254>,
) -> Result<(Proof<Bn254>, Vec<Fr>)> {
    let circuit = VaultMembershipCircuit {
        commitment: params.commitment,
        merkle_root: params.merkle_root,
        merkle_proof: params.merkle_proof,
        // private:
        preimage: params.preimage,
    };

    let (proof, public_inputs) = Groth16::<Bn254>::prove(proving_key, circuit, &mut rng)?;
    Ok((proof, public_inputs))
}
```

## On-Chain Verifier (ZkVerifier.sol)

Generated by snarkjs (`snarkjs zkey export solidityverifier`) or Nargo (`nargo codegen-verifier`). Do NOT hand-write verifier logic.

```solidity
interface IZkVerifier {
    function verify(
        uint256[2] calldata a,
        uint256[2][2] calldata b,
        uint256[2] calldata c,
        uint256[] calldata publicInputs
    ) external view returns (bool);
}

contract ZkVaultGate is AccessControlUpgradeable {
    IZkVerifier public immutable verifier;
    mapping(bytes32 => bool) public usedProofs; // nullifier → used

    function executePrivateAction(
        uint256[2] calldata a,
        uint256[2][2] calldata b,
        uint256[2] calldata c,
        uint256[] calldata publicInputs,
        bytes32 nullifier
    ) external {
        require(!usedProofs[nullifier], "Proof already used");
        require(verifier.verify(a, b, c, publicInputs), "Invalid proof");
        usedProofs[nullifier] = true;
        // ... execute action
        emit PrivateActionExecuted(nullifier, publicInputs[0]);
    }
}
```

**Critical**: Nullifier tracking prevents proof replay. Every proof must include a nullifier derived from a secret the prover knows but that doesn't reveal their identity.

## Circuit Design: Vault Membership

Proves: "I own an account in the vault Merkle tree without revealing which one."

Public inputs: `merkleRoot`, `nullifier`
Private inputs: `secret`, `accountIndex`, `merklePathElements[]`, `merklePathIndices[]`

```circom
pragma circom 2.0.0;
include "circomlib/circuits/poseidon.circom";
include "circomlib/circuits/mux1.circom";
include "circomlib/circuits/bitify.circom";

template VaultMembership(levels) {
    signal input root;
    signal input nullifierHash;
    signal private input secret;
    signal private input pathElements[levels];
    signal private input pathIndices[levels];

    // Compute commitment = Poseidon(secret)
    component commitment = Poseidon(1);
    commitment.inputs[0] <== secret;

    // Compute nullifier = Poseidon(secret, 1)
    component nullifier = Poseidon(2);
    nullifier.inputs[0] <== secret;
    nullifier.inputs[1] <== 1;
    nullifierHash === nullifier.out;

    // Merkle proof verification
    // ... standard Merkle path computation
    root === computedRoot;
}
```

## Security Considerations

| Risk | Mitigation |
|---|---|
| Proof replay | Nullifier map on-chain; nullifier is deterministic from secret |
| Trusted setup compromise (Groth16) | Use Powers of Tau ceremony output; or use Plonk (universal setup, no per-circuit ceremony) |
| Proving key exposure | Proving key stored server-side only, never sent to client |
| Private input leakage via logs | Structured logging must exclude zk API request bodies |
| Malicious circuit | Audit circuit logic independently of verifier contract |
| Verifier contract bug | Use generated verifier only; add integration tests with valid/invalid proofs |

## Trusted Setup (Groth16)

If using Groth16, the circuit-specific trusted setup (Phase 2) must be performed:
1. Download Phase 1 (Powers of Tau) — use Hermez ceremony or Zcash parameters.
2. Run Phase 2 for each circuit.
3. Contribute randomness (even a single honest contributor suffices for security).
4. Export `.zkey` and verify against `.r1cs`.

For v0.4, an internal ceremony is acceptable. For v1.0+, consider a public ceremony or switch to Plonk/UltraPlonk (no per-circuit ceremony).
