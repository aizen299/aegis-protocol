# v1.1.0 — Every module has a UI, and the zk gate is safe to drive

v1.0 shipped four working modules and a UI for one of them. This closes that gap, and closes the
one High-severity finding v1.0 shipped with.

As with v1.0: read the second section before the first.

---

## What v1.1 adds

**A UI for the whole protocol.** Ten routes: the vault dashboard, oracle feeds with round history and
per-node submissions, oracle operators, governance proposals with tallies and timelock state, and
the zk surface — gate wiring, commitments, executed private actions, and a nullifier lookup. All
read-only; nothing in this release constructs a transaction.

**ZK-1 is fixed.** v1.0 shipped knowing a proof was a bearer instrument: anyone who saw one in the
mempool could land it first and permanently burn the prover's nullifier. The proof now carries a
sixth public input naming the account permitted to submit it, and the gate reads that from
`msg.sender`. The trigger v1.0 recorded — *no contract may consume this gate until a binding exists*
— is satisfied.

**The API can be called by a browser.** It could not before. Four releases of a REST API written for
a frontend, and no browser had ever reached it, because the frontend's API client was dead code that
nothing imported. CORS now works from an allowlist that defaults to nobody.

**The frontend has tests.** 48 of them, where it previously had none — CI ran `typecheck`, `lint`,
and `build`, none of which assert behaviour.

## What v1.1 does not change

Everything `docs/v1.0-release-notes.md` says v1.0 is not, it still is not:

- **No external audit.** The review in `docs/v1.0-audit-simulation.md` is the authors reviewing their
  own work. That has not changed, and this release adds no external review.
- **No deployment, anywhere.** No AWS account exists for this project. Infrastructure is defined,
  validated, and preflight-checked, and has never been applied. Still a recorded deviation from
  `docs/project-spec.md` §5 and §7.
- **No mainnet, no funds, no custody.**
- **No staging load baseline.** The indexer-lag alarm threshold remains provisional at 300s.
- **No write actions in the UI.** Voting, queueing, executing, staking, and proving are all absent.
  The next release is where the wallet questions land, and `docs/v1.1-frontend-plan.md` §2.2 records
  the one that will bite first: a holder who never delegated has no voting power, and delegating
  today does nothing for a proposal whose snapshot has already passed.

## Three things worth knowing

**The submitter binding needed no constraint, and the first attempt at one was theatre.** The circuit
originally carried `assert(s * s == s * s)` to force the input into the constraint system. Measured
rather than assumed: the generated verifier was byte-identical with and without it, and tampering
with the submitter still invalidated the proof once it was removed. UltraHonk folds every public
input into the verification transcript, referenced or not. The line was deleted rather than left
implying a guarantee it never gave — a test holds the property instead, and will fail at index 5 if
a future toolchain stops binding unreferenced inputs.

**The submitter is deliberately outside the nullifier.** Folding it in would have made the nullifier
vary with the submitting address, so one commitment could be spent once per address — trading a
frontrunning bug for a double-spend.

**The anonymity set is stated, not implied.** At one commitment the UI says *"No anonymity at all —
a proof identifies it exactly"* rather than rendering a bare `1`. No set size is ever described as
private, safe, or anonymous, and a test holds that at every N. This is what
`docs/v0.4-zk-plan.md` §4 asked for and what no circuit can fix.

## What was found by running things

Every defect below was invisible from reading the code, and each was found by putting the system in
front of a browser or a real chain:

| Defect | How it surfaced |
|---|---|
| The API had no CORS headers at all | The UI hung on "loading…" against a live API |
| A failing fetch rendered as loading indefinitely | react-query retries with backoff and stays pending — step 2's defect one layer up, inside its own fix |
| The dashboard could not tell a failed read from an empty vault | Multicall3 was absent on a local chain; every read failed and the vault looked merely empty |
| The frontend's TypeScript had drifted from the Go structs | A new drift check failed on its first run |
| The zk invariant handler could no longer execute a valid proof | The anti-vacuity probe caught it; the suite would have passed while exercising nothing |
| The storage-layout check reported an unreadable layout as a divergence | Sent me hunting a storage change that did not exist |

## Verification

337 contract tests, 21 circuit tests, 26 zk service tests (4 proving for real against the pinned
nargo and bb), 48 frontend tests, 38 end-to-end tests, 15 backend packages. Slither clean. Storage
layouts unchanged from their v0.4.0 baselines. Generated-artifact drift checks pass for the ABIs,
the Poseidon contract, the verifier, and — new in this release — the frontend's API types against
`backend/pkg/types`.

## Accepted risks

Twelve entries in `DEFERRED.md`. ZK-1 has moved to the decided table. The ones still worth reading
first: the absent penalty for an oracle node that never submits (ORC-1), and the missing slippage
bound on vault deposits and withdrawals (VLT-1).
